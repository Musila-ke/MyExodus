## 3. Documented divergences (plan text → codebase reality)

- **D1 — Pair path.** Plan `/pairs/{pairId}/…` → actual **`/pairings/{pairId}/…`**. All plan §4.3 paths map as: `nudgeState/{senderUid}`, `nudges/{nudgeId}`, `nudgeSettings/{uid}` under `/pairings/{pairId}/`; `/nudgePushQueue/{nudgeId}` stays a root collection.
- **D2 — Device registry.** Plan `/users/{uid}/devices/{installId}` → actual **`/users/{uid}/push_installations/{installationId}`**. Reuse `selectInstallations`; do **not** create a second registry (one write path, one selection rule). **Resolved at Step 5:** the document id switches from ANDROID_ID (pre-SOS key) to the **FID** (`FirebaseInstallations.getInstance().id`, §8.12) — the same identity the dispatcher multicasts to and AD-18b acks key on, so mailbox acks follow the FID too (an ANDROID_ID ack could never satisfy the per-installation contract). The legacy ANDROID_ID-keyed document is deleted once, best-effort, **after** the first successful FID write (`PushInstallationRegistrar.register` — write-first so a failed write never removes the fallback; `deleteLegacy` failure is swallowed, registration still succeeds). `pushEligible` (§8.12 formula) rides every registration write and is optional under the rules (pre-SOS clients keep writing without it).
- **D3 — Functions language.** Plan's `functions/src/partnerSos/*.ts` → **plain CommonJS `.js`** in house style (a `partner-sos.js`-style module + wiring in `index.js`), tests under `functions/test/` with `node --test`. No TypeScript build step exists and none is added.
- **D4 — Regions.** Firestore is **`nam5`**; Functions must stay **`us-central1`** (cannot deploy to nam5). The plan's single-region assumption is satisfied by keeping the callable/triggers in `us-central1` inside the nam5 multi-region footprint.
- **D5 — Envelope AAD.** `EventCipher` has no AAD parameter today. **Landed at Step 8:** two additive methods `encryptWithAad`/`decryptWithAad` (fresh random 12-byte nonce; `nonce || ciphertext`; AAD `partner_nudge|v1|{pairId}|{nudgeId}|{senderUid}`); every pre-existing method is byte-for-byte unchanged and the existing EventCipher tests stayed green untouched. Wire encoding is `java.util.Base64` standard alphabet (house precedent: `MailboxOutboxDrainer`), which is byte-identical to android's `NO_WRAP` for this content and keeps the envelope plain-JVM testable.
- **D6 — Home architecture.** Plan assumes a Home ViewModel; there is none. **Resolved at Step 8:** the sender state machine landed as `SosViewModel` (`@HiltViewModel`, `ui/home/`) — StateFlows for `enabled`/`state`, Hilt-injected `NudgeRepository` (`accountability/sos/`, all collaborators as constructor seams). Wired the house way: `MainActivity` `by viewModels()` → `AppShell` parameter → collected once with `collectAsStateWithLifecycle` → passed as values + `onSosTap` callback into `HomeScreen`. The Reach out card renders only when the flag is on AND a pair is active (`partnerNames.isNotEmpty()`). **Rev 2026-10-04 (owner mandate):** the sender control moved off Home into a shell-level FAB + confirmation dialog (plan §8.15 rev — FR-2 / §12 AC-2 superseded there); `SosViewModel` is untouched, `onSosTap` now fires from the dialog's Send, terminal results surface as snackbars instead of the card's body line, and the roster read is hoisted to `AppShell` (`partnerNames` state, one read per Home entry) where it gates both the FAB and the pinned card. **Step 9 extended the same ruling:** the recipient inbox landed as `NudgeInboxViewModel` wired identically; §8.16's "attach the listener during Home lifecycle" is a `LaunchedEffect(contentTab)` in `AppShell` — `start()` on the Home tab, `stop()` on any other tab, with `start()` idempotent so tab re-entry never stacks listeners.
- **D7 — Home banner collapse (Step 7).** Home already carries a `PROTECTION_DEGRADATION.NOTIFICATIONS_OFF` banner when app notifications are off. When the user has a partner AND notifications are off, that banner and §8.14's "Notifications are off, so you'll miss check-ins." would stack as two notifications-off banners. Ruling: while `checkInsAtRisk` (partner present + notifications off) only the SOS banner renders — its copy already names the consequence — and the degradation banner is suppressed for that identical state. All other degradation reasons are untouched; with no partner, the degradation banner renders as before.
- **D8 — Pair targeting under N pairs (multi-user).** The plan's invariant is one active pair per user; the codebase supports N pairs with a persisted selection (`PartnerSelection.selectedPairId`, §19.5). Ruling at Step 8: the sender targets the selected pair when it names a live enrollment, else the newest enrollment — exactly the dashboard's own resolution rule — and the server independently re-verifies membership/pair-activity, so a stale local pick can only produce a clean refusal, never a misdelivery. Feeds OPD #31 (targeted vs fan-out): the plan's singular wording is satisfied; a partner-picker on the card is the upgrade path if fan-out is ever wanted.
- **D9 — Offline preflight.** FR-3's "no validated network" check uses `NET_CAPABILITY_VALIDATED` (not the INTERNET-only check the sync pass uses) so a captive portal produces the honest `NotSentOffline` instead of a doomed callable. The pending `(nudgeId, envelope)` pair survives an offline retry: an ambiguous outcome followed by a network loss still replays the identical logical request when connectivity returns (server idempotency by `nudgeId` is what makes any replay safe).
- **D10 — Unreadable newest nudge: no auto-ack, no fallback (Step 9).** §6.9 says unreadable records are "handled per existing product policy" — the codebase has no policy that sanctions silently dropping delivered data (poison-replay history: the app never silently discards records it failed to read), so the receiver does neither of the two tempting shortcuts. A newest doc that fails schema validation or decryption suppresses the card with exactly one Crashlytics non-fatal (`reportUnreadable("schema"|"decrypt")`, Decision-12 metadata contract: category only, never payload/pair/uid/envelope) and never falls back to silently rendering an older doc — the partner's latest ask must not be masked. The doc is also **not auto-acked**: "I'm here"/X remain the only writers of `ackedAt`, so an unreadable nudge still appears on the next Home entry (and a transient key-derivation failure can heal). Both behaviors are pinned in `NudgeInboxRepositoryTest` (`undecryptableNewest_reportsDecrypt_neverFallsBackToOlderDocuments`, `schemaMalformedNewest_reportsSchemaAndSuppressesTheCard`).
- **D11 — Nudge read rule split `get`/`list` (Step 9).** The plan's §8.2 read rule (`recipientUid == uid` + active pair + `expiresAt >= request.time`) cannot be a `list` rule: the engine evaluates list rules against the query's *potential* result set, and a `request.time` comparison on a field the query doesn't constrain fails with `Property expiresAt is undefined on object` — the exact §6.9 query was denied (verified against the emulator; the failure and its fix are pinned by rules-test R-F2q). The fix is already inside the plan's own wording: §8.2 scopes the expiry gate to "direct reads" (`allow get` keeps it verbatim), while §6.9 ("client ignores any record whose expiresAt is in the past even if TTL has not deleted it yet") and §17 ("Client queries apply the expiresAt check; Security Rules require unexpired access") put expiry on the client query. `allow list` therefore carries recipient + pair-active only; R-F2q proves both halves: the exact query returns a past-expiry TTL-lagging doc (client must ignore it), a `get` of that same doc is refused, a query aimed at another uid is denied, and an unfiltered recipient query is unprovable and denied. `NudgeInboxRepository.cardOf` implements the client-side ignore.
- **D13 — FCM targeting: FID send → stored registration token (2026-10-04).** The plan's dispatcher multicasts to FIDs (§8.8/AD-18b, plan lines 141/341/442/1010/1583/2040). On the rig every FID send returned `messaging/installation-id-not-registered` while the same installations' full registration tokens delivered (confirmed live + against FCM docs: FID targeting only addresses installations that re-registered via `register()`/`onRegistered()`, FCM SDK 25.1+; this app registers through the legacy `getToken()` path). `nudgeFcmMessage` now sends `tokens` (map of `token` field), batch chunking unchanged, and the ANDROID_ID→FID registry doc id stays the ledger/ack key (§4.3) — the FID is still the identity; only the FCM addressing changed. Token targeting remains supported during FCM's deprecation window; revisit when the client migrates to the new registration API. Delivery proven both directions on the rig (§5.2).
- **D14 — Check-ins channel: `partner_nudges` DEFAULT → versioned HIGH (owner ruling 2026-10-04).** The plan specifies IMPORTANCE_DEFAULT; device-verified, DEFAULT renders tray-only — no on-screen banner. The owner ruled the reach-out must appear as a heads-up popup.
