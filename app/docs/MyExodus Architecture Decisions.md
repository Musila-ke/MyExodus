**ADR \#1 Title: Mobile Client Technology Stack (Native Kotlin vs. Cross-Platform)**

**Status:** Accepted  
**Evidence:** Android Accessibility Service documentation; Google Play Policy on Unused Permissions.  
**Context:** The application requires aggressive, OS-level interception of other apps and websites to enforce restriction rules. It relies heavily on Android's background APIs, specifically AccessibilityService and UsageStatsManager. Furthermore, there is a strict non-functional requirement (the Interception Latency Limit in the V1 spec) which mandates end-to-end detection-to-overlay interception in under 1000 ms (p99), with overlay draw in under 100 ms (p99), when a restricted app is opened. Technical feasibility research indicated that bridging these low-level background services through a cross-platform framework (like React Native) introduces latency and complexity that risks violating these core requirements.  
**Decision:** The application shall be built using native OS languages to directly access system APIs. Specifically, V1 development will be strictly focused on Kotlin for the Android Client Subsystem.  
**Trade-off Accepted:** We are explicitly giving up the development speed and simplicity of writing a single, cross-platform codebase (React Native) that works on both platforms. We accept the cost of building purely for Android in V1 and eventually having to maintain a second, separate codebase (Swift) for iOS in V2.  
**Consequences:** The core blocking engine is technically feasible and can natively integrate with the OS to hit the unified interception latency target on Android: <1000 ms end-to-end (p99) with overlay draw <100 ms (p99) once triggered — see the Domain Invariant in the V1 spec. (Revision 2026-08-24: replaces the earlier "<200ms" figure, which contradicted the V1 spec's <1000 ms end-to-end target; the feasibility spike validates the final number.) As a solo developer with a tight 3-to-6 month timeline, development must be strictly focused on the Android Client Subsystem for V1, while the iOS subsystem is officially deferred to V2.

**ADR \#11 Title: Trusted Telemetry & Server-Observed Event Projections**

**Status:** Accepted  
**Evidence:** CQRS/Event Sourcing architectural patterns for data integrity; Google Play Developer Policy on data manipulation; Server-side projection patterns.  
**Context:** Relying on client-side counters (e.g., streak counts) allows users to manipulate local state to fabricate progress.  
**Decision:** We will Isolate Local Enforcement from Server-Side Projections. The mobile client shall function as an append-only event producer, streaming raw activity to the server. The backend will compute all authoritative metrics (streaks, milestones, history) via server-side event projections. (V1 scope triage: implemented initially as simple server-side counters updated idempotently from the event stream; full event replay/reconstruction is deferred — see V1 spec Scope Triage.)  
**Trade-off Accepted:** The dashboard cannot show real-time projections until the client syncs events to the server.  
**Consequences:** We ensure the "source of truth" for streaks and clean days is tamper-evident and server-observed, preserving the integrity of accountability partnerships. (Deletion semantics, revision 2026-08-24: "tamper-evident" applies while data is retained; a data subject's Right to Deletion is honored via per-user server-side crypto-shredding — see V1 spec Req 29.)

**ADR \#2 Title: Data Ownership and Local Storage (Offline-First Architecture)**  
**Status:** Accepted  
**Context:** The application has two non-negotiable domain invariants that dictate how data must be handled: The 100% Offline Rule (active restriction periods must be enforced completely even when the device has zero network connectivity) and The Encryption Mandate (sensitive user data, specifically "urge logs", must always be encrypted at rest). Because of these rules, the app cannot rely on a cloud database as its primary source of truth, as a network drop would break the core blocking engine. Furthermore, as a solo developer with a tight budget, the architecture must lean toward simple, "boring" technology rather than complex custom setups.  
**Decision:** The application will use an Offline-First Architecture. The local device will be the authoritative owner of the data. We will use a local SQLite database (via Android Room) to store the RestrictionRule, DailyUsageTracker, and HabitProgress tables, ensuring the background blocking service can instantly read rules offline. We will use SQLCipher to encrypt all highly sensitive behavioral data (urge logs, bypass attempts) at rest on the local device. (Correction, 2026-08-24: EncryptedSharedPreferences is NOT an alternative here — it encrypts flat key-value pairs and cannot back the relational schema with joins and queries that RestrictionRule, DailyUsageTracker, and HabitProgress require. SQLCipher encrypts the entire SQLite database; that is the only option for this use case.) A cloud backend (e.g., Firebase) will act only as a replica/relay to sync this data up to the accountability partner when a network connection is available.  
**Trade-off Accepted:** We are explicitly giving up the simplicity and speed of writing directly to a real-time cloud database. We accept the engineering cost and complexity of having to build an "offline-sync" mechanism (saving locally first, tracking what hasn't synced, and pushing to the cloud later) in exchange for guaranteeing 100% offline reliability and meeting strict data protection compliance.  
**Consequences:** The core blocking engine will never fail due to a bad network connection or Airplane mode. Sensitive user data remains encrypted locally, directly satisfying the legal and security mandates for handling high-risk personal data. The system can automatically enforce the Data Retention Rule by clearing out old local behavioral history on a rolling basis without needing a server to trigger the deletion.

**Source-of-Truth Note:** *The backend server computes and projects authoritative metrics (streaks, milestones) for partnership transparency, while the mobile client is responsible for enforcing local real-time restrictions regardless of sync status.*

**ADR \#3 Title: The Backend Server & Cloud Sync Strategy (Event-Driven Relay)**  
**Status:** Accepted  
**Context:** Because ADR \#2 established an Offline-First Architecture, the local SQLite database on the Android device is the primary owner of the data. However, the system must still route "relapse alerts" and "bypass attempts" to accountability partners, and populate the partner's usage analytics dashboard. Furthermore, we must stay within a strict 9,000 KES budget and accommodate a solo developer's capacity. We need a way to get offline events to the cloud securely without running an expensive, complex custom server.  
**Decision:** The application will use a Serverless Cloud Backend (e.g., Firebase) acting purely as an asynchronous sync relay and notification router. When offline, the mobile app will queue events (like a bypassed block or an incremented streak) locally. When the device regains internet connectivity, a background sync engine will push these queued events to the cloud as a single batch. The cloud backend will then automatically route push notifications to the assigned\_partnership\_id (enforcing granular consent) and update the partner's read-only replica of the dashboard.  
**Trade-off Accepted:** We are explicitly giving up the simplicity of immediate, real-time data. We accept the engineering cost of building an "eventual consistency" sync queue (handling what happens if a user is offline for 3 days and suddenly uploads a batch of relapses) in exchange for keeping server costs near zero and maintaining 100% offline blocking capability.  
**Consequences:** Accountability partners will see data with "eventual consistency" (it updates only when the restricted user's phone connects to the internet). The architecture easily fits the 9,000 KES budget constraint, as serverless databases charge only for what you sync. The cloud serves as a tamper-evident record of the user's behavioral data, providing a secondary layer of security if they attempt to modify their local database. (Clarification, 2026-08-24: "tamper-evident" means alteration is detectable — it does not mean un-deletable. Kenya's DPA grants a Right to Deletion; the server-side deletion semantics are specified in V1 spec Req 29: per-user server-side encryption keys are shredded on a deletion request, making raw events unrecoverable, while anonymized aggregates may remain.)

**ADR \#4 Title: Client Presentation and Data Architecture (MVVM Layered Presentation)**

**Status:** Accepted  
**Context:** The client application must manage complex, reactive background operations (AccessibilityService, local VPN, and WorkManager schedules) while presenting a highly responsive, low-latency block screen overlay. To maintain high velocity as a solo developer with a tight timeline, we must cleanly separate our UI layers from our persistent business rules and network synchronization.  
**Decision:** The Android client application shall be built using a Layered Presentation Architecture implementing the Model-View-ViewModel (MVVM) pattern.  
**Model:** Composed of our Room DB schemas, local SQLCipher encryption, and Firebase event-driven sync interfaces.  
**ViewModel:** Responsible for holding and preparing UI state, exposing observables (Kotlin Flows) to the View layer, completely decoupled from Android UI contexts.  
**View:** Composed of lightweight UI layouts that simply observe state emitted by the ViewModels.  
**Trade-off Accepted:** Writing formal ViewModels introduces small structural boilerplate files up front compared to direct, rapid scripting (like running database queries directly inside an Activity class). We accept this tiny setup cost to secure the massive benefits of modularity and testing.  
**Consequences:** The codebase is robust, highly maintainable, and prevents tight coupling. Views can be safely updated or redesigned without risking regressions in our sensitive background blocking and data logging services.

**ADR \#5 Title: Declarative UI and Dependency Injection**

**Status:** Accepted  
**Context:** To ensure the core blocking engine successfully hits our visual interception targets, the developer needs a modern development environment that minimizes standard layout boilerplate, makes state synchronization easy, and ensures clean lifecycle initialization without manual constructors.  
**Decision:** The application will use Jetpack Compose as the declarative UI framework and Hilt (Dagger) for compile-time Dependency Injection.  
**Trade-off Accepted:** Adopting modern Jetpack Compose and Hilt requires a small learning curve compared to legacy XML structures. However, this is heavily offset by the vast amount of modern developer documentation and the dramatic reduction in code length.  
**Consequences:** UI layout code is written directly in Kotlin, reducing the number of file types we must track. Hilt will automatically manage the creation, sharing, and teardown of crucial database instances (like our encrypted Room SQLite tables) across background services and ViewModels, preventing memory leaks and simplifying testing.

**ADR \#6 Title: Optional Device Administration & Uninstall Resilience (Direct-Distribution Only)**

**Context:** Preventing a user from simply uninstalling the application during an active relapse window is a critical non-functional requirement for habit recovery. While Android's Device Administrator API natively blocks uninstallation, Google Play Store policies strictly penalize consumer-facing apps that leverage both Accessibility Services and Device Administration APIs simultaneously, labeling it a security risk. The original architecture split builds into playRelease/directRelease to isolate that risk. **This constraint no longer exists: the project will NOT be published on Google Play (ADR#15, decision 2026-08-24) — all distribution is direct APK. The playRelease flavor is removed; there is no Play-compliant build to protect.**  
**Decision (Revision 2026-08-24, supersedes the flavor split):** All builds use the same uninstall-resistance stack:  
- **Primary Layer — Accessibility Settings Shield:** the AccessibilityService monitors the system Settings app window to discourage uninstallation.  
- **Secondary Layer — opt-in Device Administrator permission:** if enabled, standard OS uninstallation is hindered by the system. Device Admin is NEVER a default enforcement path (V1 Req 22).  
- **Baseline — PACKAGE_REMOVED broadcast:** if the app is uninstalled or critical permissions are revoked, the system immediately alerts the accountability partner and logs a high-severity tamper event (V1 Req 22).  
**Trade-off Accepted:** There is no Play-compliance reason to withhold uninstall-resistance mechanisms anymore; the remaining trade-off is user agency vs. resilience. Users can revoke permissions at any time; we accept the risk that technical users bypass these safeguards.  
**Consequences:** All distributions carry maximum uninstall resilience. The disclosure UX that Play would have required (in-app accessibility justification, persistent foreground-service notification) is still good practice and retained, but no store reviewer enforces it. The Play rejection/takedown risk identified in the V1 audit (finding C3) is moot because no Play submission exists. If a Play release is ever reconsidered, this ADR must be re-opened before submission.

**ADR \#7 Title: Self-Defense & Interception Escape Hatches**

**Status:** Accepted  
**Context:** The system must prevent locking the user out of their recovery tools, even when the device is locked down or blocked. Furthermore, we must prevent the "Self-Blocking" loophole where a user blocks MyExodus, rendering the entire system unusable and the device permanently bricked.  
**Decision:** We will programmatically allow-list the MyExodus app package within the AccessibilityService and local VPN loops, ensuring the app never blocks itself. Additionally, we will implement hard SQLite check constraints (CHECK target_identifier != 'com.example.myexodus') and business-logic validators to reject any write operation containing our host package name as a block target. (Correction, 2026-08-25: the app package name is com.example.myexodus, matching applicationId in build.gradle; earlier drafts citing 'com.ũtethyo.myexodus'/'com.utethyo.myexodus' were wrong.)  
**Trade-off Accepted:** We accept that having a visible "Open Recovery Tools" button on block overlays introduces a tempting distraction. We mitigate this by ensuring that launching the app only displays local, offline recovery resources, scripture cards, and urge logs—they cannot access general system settings or unblocked applications from this recovery space.  
**Consequences:** This guarantees the client app cannot block itself: the code allow-list and the SQLite CHECK constraint reject the app's own package as a block target, with a unit test covering the rejection path (Revision 2026-08-24: the previous "bulletproof... safe haven" wording was not falsifiable — it is now stated as a testable guarantee). The recovery dashboard remains reachable from every block overlay via the Interception Escape Hatch (V1 spec Req 25), and that reachability is covered by the FSM transition tests in the V1 testing strategy.

**ADR \#8 Title: Nairobi-Hosted Virtual Private Server (VPS) for Data Residency**

**Status: Pending — BLOCKED pending legal review of Section 50 and budget reconciliation.**  
**Context:** The V1 spec's Backend Compliance Strategy (audited version) states the system uses Firebase only "without requiring a custom Nairobi VPS replica," while this ADR previously claimed a Nairobi serving copy is mandatory under Kenya's DPA. These positions contradict each other. The audit (2026-08-24) could not verify the legal claim that the DPA requires a mirrored local serving copy — the correct reading of Section 50 is an open legal question, not a settled requirement. Separately, the ~600 KES/month VPS cost over a 6-month build (~3,600 KES) would consume ~40% of the 9,000 KES total budget before any other cost (Revision 2026-08-24: the earlier "76%" figure included Google Play registration, which is no longer budgeted — see ADR#15; the VPS alone still contradicts the "negligible cost" framing).  
**Decision (Revision 2026-08-24 — recommended: REJECT):** The Section 50 premise has been checked against the Act's primary text (Kenya Law, Act No. 24 of 2019, Section 50): it grants the Cabinet Secretary a *discretionary* power ("may prescribe") to designate certain categories of processing for grounds of state strategic interest or protection of revenue — it is **not** a self-executing requirement that every controller of sensitive personal data maintain a local serving copy, and there is no evidence it has been invoked for consumer habit-recovery apps. The specific "must be mirrored locally" justification for this ADR is therefore not supported. Recommended action: **reject this ADR and keep the Firebase-only architecture** — cross-border transfer safeguards under Sections 48-49 (SCC-based) are addressed in the V1 spec's regulatory section and ADR#3. Final confirmation from Kenyan data-protection counsel is still required before the matter is closed (V1 spec Open Research Questions, item 1(c)); if counsel identifies a narrower obligation that does apply, cite that provision rather than Section 50 before any VPS work begins.  
**Alternatives considered (Revision 2026-08-24):** a single self-hosted backend (Postgres + thin API layer) on the same Nairobi VPS was evaluated — it would consolidate the Firebase and residency decisions and remove the dual-write complexity. Rejected for V1 because self-hosting adds operational burden (backups, patching, uptime) for a solo developer on a 3-6 month timeline; it is revisited only if the legal analysis changes.  
**Trade-off Accepted (if ever built):** Maintaining a secondary sync endpoint adds slight network complexity to the mobile sync queue, offset by residency compliance. The "~600 KES/month" figure (Angani / Kenya Web Experts) is unverified pricing and must be replaced with a written quote before acceptance.  
**Consequences:** If rejected (the recommended path), V1 stays Firebase-only within the 9,000 KES budget. If counsel later identifies a binding requirement, this ADR is re-opened with a proper decision. Do not implement until the counsel review concludes.

**ADR \#9 Title: Hardware-Backed Dynamic Database Encryption**

**Status:** Accepted  
**Evidence:** Android Keystore System API documentation; SQLCipher security best practices.  
**Context:** Static encryption keys are insecure, but keys bound solely to hardware (Android Keystore) prevent database recovery after a factory reset or device upgrade, causing a recovery paradox.  
**Decision:** We will enforce standard Android Keystore-backed key protection. The SQLCipher passphrase is encrypted at runtime via a non-exportable, hardware-backed key managed by the Android Keystore.  
**Escrow scheme (Revision 2026-08-24, audit H1 — previously the scheme was a name with no design):** for device migration, the app exports an encrypted escrow copy of the database passphrase protected by a user-chosen recovery phrase — the standard "encrypted backup + recovery phrase" pattern used by mainstream messaging apps (see V1 spec Req 28). The backend holds only a signed verification blob and **never the raw key or passphrase**, so a server compromise cannot decrypt user history. No threshold-secret-sharing or custom split-key scheme is implemented (custom cryptography is out of scope for a solo developer — V1 spec Scope Triage).  
**Trade-off Accepted:** Increased complexity in the account migration and recovery flow: the user must remember their recovery phrase; losing it after a device change means local history cannot be restored (accepted — this mirrors the inherent trade-off of hardware-bound keys).  
**Consequences:** We maintain high-grade security for local data. While hardware-backed protection significantly raises the bar, recovery on new devices requires the recovery-phrase migration workflow described above, which must be covered by a tested end-to-end migration test before release (V1 testing strategy).

**ADR \#10 Title: Secure Direct-APK Update Verification Subsystem**

**Status:** Accepted  
**Context:** With no Play Store distribution (ADR#15), **every** MyExodus update is a direct APK download — there is no store-mediated signature verification for any user. To protect the software supply chain, we must prevent attackers from hosting a malicious or modified version of MyExodus.apk on a hijacked distribution URL, and we must ensure update integrity across certificate rotations. (Consolidated 2026-08-24, audit C1: two interleaved versions of this ADR existed; this is the authoritative one — the earlier "trusted signing lineage" wording described the same decision.)  
**Decision:** The in-app updater shall never execute a blind download-and-install. All update metadata manifests must be signed cryptographically with our private release key. The on-device updater must download the manifest over HTTPS, verify its signature, and programmatically verify that the downloaded APK's package name, version code, and SHA-256 certificate fingerprint exactly match our permanent release signing profile before launching the Android Package Installer.  
**Trade-off Accepted:** Slower update implementation due to required manual manifest management and key handling.  
**Consequences:** This creates a cryptographically hardened update path, preventing unauthorized or malicious APKs from being installed via the in-app updater.  
**Release-Signing-Key Runbook (Revision 2026-08-24, audit H4 — previously no key-rotation or compromise-recovery plan existed):** (1) the release signing key is generated on an offline machine and stored in two cold locations (e.g., encrypted USB and a printed backup in a safe) — it never lives on the developer laptop; (2) it is distinct from the debug signing key; (3) rotation: Android supports key rotation via the signing-lineage file — store the lineage in the repo and re-issue it on each rotation; (4) compromise/loss response: treat suspicion of compromise as compromise — stop issuing updates immediately, rotate the key, publish a signed update over the existing verified channel announcing the rotation, and notify direct-distribution users; a leaked key can sign malicious "verified" updates, which is the single point of failure for this ADR's integrity guarantee.

**Update-channel & trust practice (Revision 2026-08-24, follows the ADR-log audit):** This ADR is the app's OTA mechanism — native Kotlin has no EAS/CodePush-style bundle updates, so every code change ships as a new signed APK via this flow. Implementation specifics: (1) the update check is a periodic WorkManager job (e.g., daily) hitting the signed manifest URL — no always-on daemon; (2) Firebase Remote Config covers non-code changes (feature flags, copy, rule defaults) so those never require an APK; (3) AV false-positive practice: never ship a debug-signed release, keep the permanent release key stable, upload each release APK to VirusTotal, and use each vendor's false-positive report page if it flags us; (4) Android 13+ shows an "unknown app" screen on fresh sideloads (unavoidable, no Play distribution) — onboarding must walk users through it; same-signature updates install without that friction, which is why users must always update in place via this flow, never re-download the APK.

**ADR \#12 Title: Confidence-Level Tamper Model**

**Status:** Accepted  
**Context:** The blocking engine must detect when enforcement is silently failing — not just when a user bypasses a block, but when they disable permissions, roll back the clock, or kill the service. The V1 spec defines confidence levels for tamper detection (Req 23, Epic 2 Step 7), but this decision had no ADR of its own. (Added 2026-08-24, audit L2.)
**Decision:** We will implement the confidence-level tamper model as specified in V1 Req 23 / Epic 2 Step 7: the app scores multiple signals into low/medium/high confidence that enforcement is active, and high-confidence tamper escalates to the accountability partner per the alerting rules. Signals: AccessibilityService binding status; Device Admin state (available in all builds — the directRelease-only scoping was removed with the Play flavor split, ADR#6/#15); `Settings.Secure` package-presence queries for known bypass tools; clock-change detection with timezone-vs-tamper disambiguation (compare wall clock against network time / elapsed-realtime); and PACKAGE_REMOVED / permission-revocation broadcasts. No separate anti-tamper SDK is used (V1 Scope Triage).
**Trade-off Accepted:** Some signals (package-presence scans, clock checks) cost battery and can produce false positives; we accept occasional misclassification over silent enforcement failure — this is the pre-mortem item "silent enforcement failure" made observable.
**Consequences:** Enforcement failures are visible to the partner instead of silent; the confidence score drives alert severity. The disambiguation and scoring logic is covered by unit tests in the V1 testing strategy.

**ADR \#13 Title: Observability & Crash Reporting**

**Status:** Accepted  
**Context:** V1's Step 12 (post-release monitoring) requires crash reporting and usage monitoring, but no ADR recorded the tooling choice. A solo developer cannot operate a self-hosted observability backend on the 9,000 KES budget. (Added 2026-08-24, audit Missing Research 2.)
**Decision:** We will use Firebase Crashlytics for crash/ANR reporting and Firebase Analytics for basic usage monitoring — both are already in the Firebase BoM, so no new dependency or cost. No custom log pipeline, no self-hosted Grafana, no third-party crash SDK. Telemetry is metadata-only: crash contexts are scrubbed of user behavioral data (urge logs, block history) before upload, consistent with the data-minimization posture in Req 29 and the compliance section.
**Trade-off Accepted:** Crashlytics offers no session replay or fine-grained tracing; the marginal debugging value does not justify operating a custom pipeline for a solo developer.
**Consequences:** Crashes and ANRs appear in the Firebase console with de-identified metadata; user content never leaves the device via telemetry; crash-free rate is tracked against the Step 12 release gate.

**ADR \#14 Title: CI/CD & Release Automation**

**Status:** Accepted  
**Context:** The plan requires automated checks on every change (lint, unit tests), and directRelease updates demand reproducible builds, but no ADR recorded the pipeline or the signing model. (Added 2026-08-24, audit Missing Research 3.)
**Decision:** We will use GitHub Actions for CI: on every push/PR, run `./gradlew :app:lintDebug :app:testDebugUnitTest :app:assembleDebug`. CI artifacts are unsigned or debug-signed and never distributed. Release builds are signed locally per the ADR#10 Release-Signing-Key Runbook (offline key, cold storage) — the signing key never enters CI. Releases are signed and uploaded from the developer machine, not from CI. (Revision 2026-08-24: "Play and direct releases" → "releases" — there is no Play distribution, ADR#15. V1 scope triage: fully automated release pipelines are deferred.)
**Trade-off Accepted:** A manual signing/upload step on each release; acceptable because releases are infrequent and putting the release key into CI would contradict ADR#10's offline-key rule.
**Consequences:** Every change is verified by lint + unit tests before merge; release integrity rests on offline key discipline, not CI infrastructure; the pipeline fits the 9,000 KES budget (GitHub Actions free tier).

**ADR \#16 Title: Secure Persistence Layer (SQLCipher + Keystore-Wrapped DEK)**

**Status:** Accepted  
**Context:** V1 requires all on-device persistence to be encrypted (V1 Req 20 area; secure-persistence implementation plan, 2026-08-25). The database must remain readable only with a device-local key, and a compromised host machine must not be able to extract data from a stolen database file alone. No plaintext database has ever shipped, so plaintext-to-encrypted migration is dead code for this install base.
**Decision:** Room 3 (androidx.room3) on SQLCipher 4.18 via SQLCipherDriver, with a 256-bit random DEK wrapped by a Keystore-resident AES-256-GCM KEK (StrongBox opportunistic, TEE fallback). The wrapped DEK (IV + ciphertext + tag) lives in a private SharedPreferences file; the DEK is only ever a ByteArray, never a String, never logged. Six entities as scoped in V1 (Partnership deliberately out of scope). CHECK constraints (Rule 4 self-block, severity values) and the single-active-profile partial index are created via raw SQL in a RoomDatabase.Callback.onCreate because Room's annotation processor cannot express them; the restriction_rules table is rebuilt under a SAVEPOINT (SQLite cannot ALTER-ADD a CHECK; Room 3 wraps schema setup in a transaction). Failure classification routes every open failure into a defined DatabaseHealth state (Ready / RecoverableDataFound / DatabaseIssue / KeyUnavailable / Transient), RecoveryManager is the sole file-deletion authority, and SQLITE_BUSY is retried 3x with 200/500/1000 ms backoff. `android:allowBackup="false"`; dependencyLocking lockAllConfigurations; R8 currently disabled; net.zetetic keep rules are pre-seeded in proguard-rules.pro (plan Section 13, revisit at first release build).
**Trade-off Accepted:** Keystore KEK means a wiped/relocated Keystore (factory reset, some OEM transfers) makes existing data unrecoverable — accepted, and it is the entire point of the threat model (offline extraction of device or storage). Message-based busy detection (getErrorCode() is API 30+; minSdk 24).
**Consequences:** Database files are unreadable without the on-device key; a fresh install creates a new DEK. The recovery UI surfaces key loss, corruption, and recoverable-data states instead of crashing. DomainEvent ledger is append-only at the DAO layer for sync idempotency by (installation_id, event_id).

**ADR \#18 Title: Accountability-Partner Protocol (E2EE, plan `accountability-partner-protocol-implementation-plan.md`)**

**Status:** Accepted; implementation complete 2026-08-29 (phases 1-6; unit suite green, lint zero). Remaining: §12 device matrix, Firestore rules deployment + App Check enforcement (§18, user step).
**Context:** V1 §16's partner dashboard/alerting needs an event channel that a malicious relay cannot read, forge, or reorder. **Trade-off Accepted:** Single-device validation cannot prove OEM-agnostic behavior; the relaxation trades that proof for progress (no second device exists). Mitigation: the fixes are in-app correctness bugs (ISN stability, ACK flag), not workarounds for XOS quirks, so the portability risk of the *sinkhole itself* is unchanged by the bug fixes.

**ADR \#22 Title: Secrets Storage (Slice 6) — DataStore + Tink Vault, Decision 12 Remediation**

**Status:** Accepted; implementation complete 2026-08-30 — unit suite green (new secrets tests + IdentityEpoch migration suite), lint zero.
**Context:** Plan §8.6 stores the pairing key + escape code (Decision 11: the secrets set is exactly these two) behind a Tink AEAD DataStore; Decision 12 bans EncryptedSharedPreferences/security-crypto (Tink is the forward direction, §17 AC#8: a plaintext dump of Device-Protected Storage yields nothing). §12 requires the Keystore-loss path — ciphertext on disk, Keystore master key gone — to surface as a recoverable corrupted state, not a crash or lockout. (3) **Decision 12 remediation:** `IdentityEpochStore` migrated off EncryptedSharedPreferences to Room — `identity_epoch` singleton-row table (id 0), DAO `current()`/`upsert()`, DB version 2→3 with `MIGRATION_2_3` (plain DDL, no data transformation); `AccountabilityModule` drops all security-crypto imports. (4) **API pins (alpha10 KMP reality):** DataStore 1.3.0-alpha10 moved the serializer into `FileStorage` (the old `PreferenceDataStoreFactory.create(serializer=...)` signature is gone — javap-verified); datastore-tink's android variant depends on tink-android 1.20.0 transitively, pinned explicitly to 1.23.0 for the Tink 2.x-style API (`RegistryConfiguration.get()`, `KeyTemplate.createFrom(PredefinedAeadParameters)`). **ADR \#23 Title: Partner Pairing Protocol (Slice 7) — Token-Ride Payload, Null-Resource Rules, SET-Encoded Purpose, Biometric Two-Path**

**Status:** Accepted; implementation complete 2026-08-30 — full §10 round trip paired both roles on the Infinix X6532 (SAS agreed 91762 both sides) and §10 step 4 revocation returned Deleted.
**Context:** Plan §7 step 8 + §10 steps 1-5 require: single-use time-limited pairing token in a QR; the token exchanged for device-identity registration through the Firebase relay; token invalidated after first use/expiry; either party can revoke; re-pairing needs a fresh token. §6.1 adds the transcript-bound SAS: both devices sign T and exchange signatures before the CEK derivation. The on-device harness (PairingTestActivity, debug) is the §12 verification vehicle — and it caught three real production defects the JVM suite could not.
**Decision:** (1) **QR overflow → payload rides the token document.** A real Android attestation chain (leaf + intermediates) is ~5.2 KB — over the QR v40 binary ceiling (2953 B); ZXing throws WriterException("Data too big"). The QR now carries only the single-use token + pair id (~120 bytes); the initiator's enrollment payload (attested chain, challenge, agreement key) is stored in the token document and returned by the redemption transaction — possession of the token (QR) remains the sole gate (§10 step 2). The wrapper pairId must equal the token's, or the content is rejected before touching the relay. (2) **Transcript signatures are pair-document fields, not payload material.** Both signatures land as top-level pair-doc fields: the partner's via `confirmPartnerSignature` right after redemption (its transcript is buildable once the initiator's agreement key arrives from the token doc — §6.1 ordering), the initiator's via `confirmPairing` after the SAS check. `EnrollmentPayload.transcriptSignature` was removed. (3) **Firestore rules null-resource trap.** Rules deny reads of *nonexistent* docs (`resource.data.members[...]` evaluates false on a null resource), so the redemption transaction's pre-create read of the pair doc aborted with PERMISSION_DENIED, which the exchange mapped to TokenExpired on a 20-second-old token. Fix: `pairs` allow read/update/delete if `resource == null || request.auth.uid in resource.data.members`; `pairing_tokens` allow read/delete if `resource == null || resource.data.expiresAt > request.time` — reads of missing docs resolve to null instead of being denied, while existing docs stay membership-gated. (4) **Keymaster encodes purpose as `[1] EXPLICIT SET OF INTEGER` — a DER SET, not a sequence.** BC's strict `ASN1Sequence.getInstance(tagged, true)` throws IllegalStateException("unexpected explicit encoding") on the ASN1Set the parser returns; the JVM fixture built a SEQUENCE, so only the device caught it. Fix: unwrap the tagged content (`getBaseObject()`) and accept either collection type; the origin tag is read the same unwrapped way (implicit/explicit agnostic). (5) **Biometric two-path prompt (keystore2 on API 34).** `Signature.initSign` on an AUTH_BIOMETRIC_STRONG key throws UserNotAuthenticatedException without a fresh auth token, and a CryptoObject with an uninitialized primitive crashes at getOpId; `PromptInfo.Builder` requires `setNegativeButtonText` when BIOMETRIC_STRONG-only. The harness prompts with the CryptoObject when initSign succeeds, and without it (initSign inside `onAuthenticationSucceeded`) when keystore2 demands a fresh token — the 900s auth window (NFR4) covers the signature. Production UI will mirror this pattern.
**Verification:** On-device full round trip (single X6532 running both roles against the real Firestore relay): token generated → QR cached → partner redeemed (biometric) → PARTNER VERIFIED, SAS 91762 → initiator signed (biometric) → `partner outcome: Paired(pairId=0b06f15c93337798, sas=91762)` + `initiator outcome: Paired(..., sas=91762)` — SAS agreed; then Delete pair → `deletion result: Deleted`. Each defect above was first reproduced on-device (WriterException, TokenExpired-at-20s, IllegalStateException, UserNotAuthenticatedException/CryptoObject crash) and its fix regression-tested: `PairingFlowTest` (full round trip, expiry, reuse, corrupt-signature, corrupt-payload, mismatched-pairId, timeout), `PairingCodecTest` (round trip, <200 B under the QR ceiling, pairId mismatch), `AttestationVerifierTest.purposeEncodedAsSetOf_isParsedWithoutCrashing` (fixture now emits the real SET + [702] origin encodings), `FirestoreSchemaTest` (payload Blob in token data, rules contract). Full unit suite green; lint zero; rules deployed 2026-08-30.
**Trade-off Accepted:** Single-device verification runs both roles in one process — the protocol's device-to-device interaction is only through the relay, so the code paths are identical, but true two-device concurrency and a real camera QR scan wait for Slice 11's device matrix (the emulator is available if a second live device is needed sooner). The abort paths delete pair state on verification failure but a timed-out initiator leaves an orphan pair document (dev-project litter, harmless — members-gated and unreachable without the pair id); cleanup semantics for abandoned pairings are deferred to production UI. Biometrics remain the only signing gate (NFR4); users without any enrolled biometric or device credential cannot pair — a V1 UI decision (recommended: `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`), flagged for the V1 pairing screens plan.
**Revision 2026-08-30 (V1 pairing auth & multi-device resolution, researched against developer.android.com):** (1) **Signing-gate chain for users without biometrics.** Devices with a PIN/pattern/password but no biometrics pair via the device credential: API 30+ `setAllowedAuthenticators(BIOMETRIC_STRONG or DEVICE_CREDENTIAL)` + `BiometricManager.canAuthenticate(same combo)` (returns SUCCESS when either exists); API 26–29 (post-Slice-10 minSdk floor) cannot express DEVICE_CREDENTIAL in `setAllowedAuthenticators` — gate on `KeyguardManager.isDeviceSecure()` and use the legacy `setDeviceCredentialAllowed(true)` path (kept out of the current code until the V1 pairing UI lands; the Slice 7 two-path CryptoObject prompt pattern stays the template). (2) **Devices with neither biometrics nor a device lock** (`isDeviceSecure() == false`): `BiometricPrompt` answers `ERROR_NO_DEVICE_CREDENTIAL`/`ERROR_NO_BIOMETRICS`; the app cannot force a lock and must not invent an app-level password — pairing is gated on the enrollment intent (`Settings.ACTION_BIOMETRIC_ENROLL` with `EXTRA_BIOMETRIC_AUTHENTICATORS_ALLOWED`, per the official fallback docs) and a clear "set a screen lock to pair" screen. Rationale: an unsecured device cannot meaningfully anchor the attested-enrollment security posture (§10), and app-level PINs are a second password system that dilutes the partner-accountability threat model (Rejected for V1). The escape hatch (override/recovery friction) stays biometric-free — a no-auth user is never locked out of the phone, only out of pairing. (3) **Multi-device operation.** Enforcement is per-device and fully local (each device's engines read its own Room snapshot; the FGS/overlay/DNS blockers never depend on the peer); pairing connects only the accountability layer through the Firebase relay (token exchange, transcript signatures, partner alerts via the Slice 9 outbox). Both pairing roles were exercised on-device against the real relay in this ADR's Verification; the honest residual gaps are real two-device concurrency, a camera QR scan, and the outbox round trip — scheduled for Slice 11 (§12 matrix; emulator stands in earlier if needed).
**Consequences:** Plan §7 step 8 + §10 steps 1-5 + §6.1 + NFR4 satisfied on the single available device. ADR #22's SecretsRepository now stores the derived pairing key; the enrollment record (mirror, both sides) is persisted. Next per plan order: §8.5-adjacent foreground service (Slice 8).

**ADR \#28 Title: Full-Project Review Pass (2026-08-31) — Protocol Hardening, Blocking-Path Fixes, Rules Tombstone**

**Status:** Accepted; implementation complete + verified 2026-08-31 (pre-V1-UI full-project code review; five-axis review per `code-review-and-quality`, cross-checked against every accepted ADR and the plan decision tables).
**Context:** Before the V1 UI workstream starts, the entire project was reviewed end to end (correctness/readability/architecture/security/performance) with the question "will this break live, or in 6 months". The review produced 13 fixes across three subsystems plus four flagged product decisions below. Every fix is a root-cause repair of a real defect or an accepted-plan invariant that the code had drifted from — none is speculative hardening.
**Decision:** (1) **CEK pair-domain separation (accountability).** `CekDerivation.deriveCek` now takes `pairId` and includes it in the HKDF info (`"StrictMode-CEK" || pairId`). Previously the CEK was derived from the ECDH shared secret alone; with the shared secret rotating only on re-pair, two pairs made with the same key material would share a CEK and, because destruction is device-level (§10), one pair's shred would free the other's ciphertext. Pair-binding keeps each pair's chain under its own key domain. Safe for existing pairs: re-pairing derives a fresh CEK, and old ciphertext is never pulled again. (2) **Bilateral deletion drains the FULL outbox, not just the request (accountability).** `initiate()` loops drain batches until `Sent(0)`, bounded by `MAX_DRAIN_BATCHES = 40` (2x the Req 27 chain cap of 1000 at batch size 50); the agreement key dies with everything encrypted under it, so shredding while older events still sit in the outbox would strand them forever. `PermissionDenied` and relay `Failed` keep their §9 semantics. (3) **Mailbox pull watermark (accountability, quota fix).** `FirestoreMailboxReceiver.pull` now advances a persisted per-pair watermark (`enrollments.mailbox_watermark_ts`, Room v4, MIGRATION_3_4) and queries `startAfter` it — the free-tier 50k-reads/day cap was being consumed re-reading the entire mailbox on every 15-min worker tick. Requires the composite index `(pairId, partnerUid, createdAt)` — deployed via `firestore.indexes.json`. (4) **Task→suspend bridge consolidated.** Four files each carried a private `await()`; now one canonical `FirestoreTasks.await` (withContext(IO) + suspendCancellableCoroutine), 11 call sites. (5) **Chain gap-recovery fork guard.** `ChainStateStore.fillGap` now checks the stored head's `previousEventHash` against the chain head and flags a fork instead of appending a mismatched sequence (previously a malicious/errant gap-fill could attach to the wrong head and silently produce a fork in store state). (6) **Chain-head optimization.** `EventCreator` reads the local head via a new `localHead(pairId, senderKeyId)` query instead of loading the full chain and filtering — same semantics, no O(n) load per event. (7) **Tapjacking (blocking, Security).** `BlockerActivity` sets `window.decorView.filterTouchesWhenObscured = true` — the blocked app could previously draw over the block screen and capture taps on override/escape. The Compose `ui-security` artifact's filter is NOT a dependency (verified in sources); the View API covers the whole window. (8) **Overlay-permission revocation detection (blocking).** New `ProtectionDegradation.OVERLAY_REVOKED`: on Transsion/XOS the blocking overlay needs the `SYSTEM_ALERT_WINDOW` appop, which can be revoked; the FGS health tick now checks it, the FGS notification reports the degradation, and the MainActivity banner offers the fix intent. (9) **Call-UI title spoof fix (blocking).** Window-title markers ("Incoming call", "In-Call UI") are now trusted ONLY on non-application windows: an app fully controls its own window title, so a hostile app could previously exempt itself by faking an incoming-call title. App-hosted call UI stays protected via the live dialer query + fallback package list. (10) **Binder round-trip pruned (blocking, performance).** `getWindows()` is only called for window-state-changed events; content-changed events resolve their display from the event (API 33+) or default display. (11) **Notification-ID collision.** Health alert moved 1001→1003 — 1001 is the FGS "Protection active" notification; a shared id would have replaced it with the health alert. (12) **Migration DEK zeroing (data).** `DatabaseMigration` zeroes the legacy DEK after the pass (`Arrays.fill` in `finally`), same contract as the activity-log key. (13) **Revocation tombstone (accountability, Security).** After §10 deletion removes the pair doc, either former member could re-create it (members is self-asserted) and reopen the mailbox. `BilateralDeletion` now writes an append-only `deleted_pairs/{pairId}` doc BEFORE deleting the pair doc (the rules gate the tombstone's create on the pair doc existing + membership), and the pair create rule denies re-creation when a tombstone exists. Tombstone write is best-effort (`runCatching` + warn): the bilateral contract (transmit, shred, wipe) must not hinge on a hardening write. Deployed to production `myexodus-53804` (rules + composite index) after the full suite passed. **(Corrected 2026-09-13, ADR #33:** the composite index was not actually live — `firebase.json` carried no `indexes` key, so the index deploy was a silent no-op; genuinely deployed + built 2026-09-13. Also, the production Hilt builder omitted `MIGRATION_3_4` — defined here and registered in the test path, but not in production — so any existing v3 DB failed every open until 2026-09-13.**)**
**Verification:** Full unit suite green — 335 tests (new/updated: `BilateralDeletionTest` drain-loop order + `tombstoneFailure_doesNotBlockDeletion`, `CekDerivationTest` pair-domain, migration-chain tests now register MIGRATION_3_4, `PairingFlowTest` fake DAO gains the watermark method, `EmergencyExclusionManagerTest` title-spoof cases flipped); lint zero (this pass also surfaced + fixed three regressions: `AccessibilityRecord.getDisplayId` is API 33 not 24 — the earlier comment was wrong, gate added; two `Uri.parse`→`toUri` KTX; one `mutableStateOf(0L)`→`mutableLongStateOf`); `assembleDebug` builds; Firestore rules compiled + released server-side.
**Trade-off Accepted:** (a) Tombstone write is best-effort — a relay failure at that instant leaves the pre-tombstone gap until the next deletion attempt; accepted because the gap is only exploitable by a former member deliberately re-creating the doc (the app never does). (b) Below API 33, non-WSC events assume the default display (correct on every single-display device, which is the whole supported fleet). (c) `attempt_log` (ADR #25) remains plain-FBE in `myexodus_rules.db` — **FLAGGED for the user**: V1 Epic 2 Step 10 mandates SQLCipher for behavioral data, and `ActivityLogStore` (the only SQLCipher behavioral store) is currently dead code; encrypting attempt_log or routing attempts through ActivityLogStore is a product decision (flagged, not silently changed).

**ADR \#29 Title: Blocking Overlay as an Interactive Pause Card — Interception Escape Hatch Realised, Attempt Logging on URL Blocks, NFR-S10 Touch Filter**

**Status:** Accepted; implementation complete 2026-09-13 (user-directed; V1-doc conformance on the shipped URL block path).
**Context:** ADR #7 accepted a visible "Open Recovery Tools" button on block overlays as a deliberate trade-off and asserted that "the recovery dashboard remains reachable from every block overlay via the Interception Escape Hatch (V1 spec Req 25)". The shipped overlay did not have it: `OverlayController` drew a full-screen opaque scrim with a single message line and zero interactive elements. A user who landed on a blocked URL was therefore in a dead end — the page behind was unreadable and untouched, and the only ways out were home/back out of the browser or disabling the blocker in Settings. The V1 doc's glossary defines the Interception Escape Hatch as "a dedicated link embedded directly into the active blocking overlays allowing instant, single-tap navigation back to the local MyExodus recovery dashboard", State 2 Path A names the button "Open MyExodus Recovery", and the NFRs require "a maximum of 1 tap for the user to access recovery resources from the active block screen" and `setFilterTouchesWhenObscured(true)` on all block overlays (NFR-S10). Two further gaps surfaced in the same pass: URL blocks never recorded an attempt, though State 2 requires `access_attempts_count` to increment on intercept; and the scrim's alpha (0xEE) left the blocked page faintly readable. A user question drove the fix — "what if the user comes back to the browser and genuinely wants a different site?" — and the user chose, from presented options, an **interactive overlay card** over relaunching the block Activity.
**Decision:** The overlay renders content-driven UI instead of a fixed message. (1) **`BlockOverlayView` + `OverlayContent`** — a `sealed interface` with `AppBlocked` (current behaviour: title + message, every action `GONE`) and `UrlBlocked(host, ruleId, browserPackage)`, which names the blocked site and shows two buttons. The action-free app cover is deliberate: a non-browser window under an overlay has no "different site" to offer and no rule-bound recovery session to start, so the card stays a wall. (**Superseded 2026-09-13 by ADR #32** — user-directed one block language: the app cover now names the app and carries the rule's single recovery action; only the different-site action stays URL-only.) (2) **Action 1 — "Open MyExodus Recovery".** `RecoveryStateStore.startRecovery(ruleId)` runs first (the same call `BlockerActivity` makes, so the Req 13 friction timer and the override cooldown are identical, not a parallel path), then `MainActivity` is started with `EXTRA_START_TAB = TAB_RECOVERY`, which `AppShell` consumes into the Recovery tab. The ruleId comes from a new `BlockDecisionEngine.matchingUrlRule(canonical)`, which `decideUrl` also now calls — one matcher, so the rule the overlay names is by construction the rule that blocked. (3) **Action 2 — "Go to a different site".** An `ACTION_VIEW` intent for `about:blank` targeted at the blocked browser's own package: one tap lands on a blank page in the same browser, and because the blocked tab remains in history a single back-step re-blocks it. This is the escape the dead end lacked, and it is honest — it does not lift the block, it leaves the blocked page. (4) **Attempt logging on URL blocks.** The intercept records to `attempt_log` via the shipped `AttemptRecorder.recordBlocked(ruleId, host)`, gated on `firstShow` so a re-render or a duplicate event does not inflate the count (State 2 increments once per intercept). Before this, only app blocks were counted, so the Rules screen showed "No attempts yet" for a website rule that had blocked dozens of times — a dishonest status surface. (5) **NFR-S10 + opacity.** `filterTouchesWhenObscured = true` on the view and the background raised to fully opaque. (6) **Mechanism unchanged.** The URL intercept still uses the accessibility overlay already chosen by ADR #17/#21 — `TYPE_ACCESSIBILITY_OVERLAY` via `Dialog`, or bare `TYPE_APPLICATION_OVERLAY` on Transsion/XOS where the accessibility overlay type is rejected. No `attachAccessibilityOverlayToDisplay` re-architecture, no new service, no schema change; `BlockerActivity` remains the app-block surface. The overlay is per-display cached and re-`bind`s its content on every show, so one instance serves every block type.
**Verification:** Unit: `BlockOverlayViewTest` (new — URL block exposes exactly the two labels, each carrying the right payload to its callback; rebinding to `AppBlocked` hides them all) and the updated `OverlayControllerTest`/`BrowserUrlScannerTest` for the widened callback. **ADR \#30 Title: Device-Test Sweep on the URL Pause Card — Scan-Decides Allow Path, Page-Like Omnibox Rule, Bar-Free Card Bounds, Display-Sized Cover, Runtime Browser-Toolbar Discovery**

**Status:** Accepted; implementation complete + device-verified 2026-09-13 (same-day sweep following ADR #29's device testing; every fix is a root-cause repair of a device-caught defect, none speculative).
**Context:** ADR #29 shipped the URL pause card with a ~2-of-5 non-persistence caveat. The same-day device-testing sweep on the X6532 root-caused it and surfaced four adjacent defects, all caught with the card live. (1) **The non-persistence:** a browser window-state-changed event (page load, tab switch) carries no URL evidence, decided Allow, and hid the card with no re-scan — device-reproduced 8/8 before the fix. (2) **Omnibox false Allows:** the scanner decided on non-page address-bar text — mid-typing fragments ("ex") and the omnibox's own hint ("Search or type URL") canonicalize to a dotless host that matches nothing, yet Allow lifted the card over a still-blocked page. (3) **Nav-bar touch loss:** a full-display card drew above the navigation bar and swallowed its touches, so Home/Back stopped working with the card up — directly contradicting the card's own hint ("Home and back always work"). (4) **Sub-window-sized cover:** a cold launch can fire the blocked app's sub-window (loading/transient dialog) before its main window; the already-shown gate then froze the cover at that sub-window's size — AnkiDroid rendered readable around a 684×563 card. (5) **Package allowlist (user-raised the same day):** real devices carry arbitrary browsers; an allowlist can only ever cover browsers someone listed.
**Decision:** (1) **The scan is the single decider for URL cards.** The Allow path no longer hides a URL card on a browser's window-state event: when a URL card is up and the event's package is that browser, the scanner is re-asked for the address bar and only its verdict decides — evidence decides, not arrival order. Non-browser Allows (app block lifted, plain app switch) still hide; the browser probe sits behind the content check so the common case never probes. (2) **Page-like text only.** Address-bar text decides only when it is page-like — an explicit `scheme:` prefix or a dotted host — unless a rule matches it outright; everything else is a logged no-op (`BrowserUrlScanner`). (3) **Card bounds stop at the system bars.** The cover is sized to the display area minus the system bars (API 30+ `WindowInsets`; full display below R), so the navigation bar stays visible and its touches never reach the card. (4) **The cover sizes to the display, not the deciding window.** A block transition shows display bounds — the sub-window freeze is fixed by construction — while split-screen pane coverage for other restricted windows stays with `blockOtherRestrictedWindows`. (5) **Runtime browser-toolbar discovery replaces the package map.** `BrowserUrlScanner.viewIdFor` probes a small set of conventional toolbar IDs (`url_bar`, `url_bar_text`, `location_bar_text`) inside the event package's own tree, memoizes per package, and retries after 10 s — any browser exposing a conventional toolbar id is scanned with no code change. Brave was first added to the map (address-bar id verified from the installed APK's resources), then the map itself was retired. The enhanced-mode plan's Step 7 carries the revision and the maintenance point (a browser with none of the candidate IDs still needs one list entry).
**Verification:** Unit suite green; lint zero. Device (Infinix X6532/XOS, 2026-09-13) — **12 consecutive fresh blocked-page loads: the card stayed up throughout, exactly one recorded attempt each, zero hidden-after-shown events; the phone's own Home/Back buttons were visible and functional with the card up (real taps); the AnkiDroid cold launch renders the cover at display size (the 684×563 freeze gone); toolbar discovery exercised against the installed Brave browser (toolbar located in its own tree, no map entry).** The scan-decides Allow path is what makes each of the 12 loads one attempt instead of one hidden-card incident.
**Trade-off Accepted:** (a) The re-ask costs one probe per browser WSC while a card is up (memoized; failed probes retried every 10 s) — accepted so evidence, not arrival order, decides. (b) A dotless, schemeless real address is not scanned — the omnibox adds the scheme on navigation and real web addresses carry a dot, so actual page loads stay page-like; a logged no-op, never a hidden card. (c) The card does not cover the system bars — that is the point (their touches never route through the cover, and the State 2 Path B guarantee holds). (d) A browser whose toolbar is absent at first probe (fullscreen video, first paint) is unscanned for up to the 10 s retry window — bounded, and it cannot stay invisible for the process lifetime.
**Consequences:** ADR #29's persistence caveat is closed with a root cause rather than a retry; URL blocking has one decider (the scan) end to end; the card can no longer contradict its own hint; the per-browser maintenance burden is retired for conventional toolbars. V1 doc's pause-card bullet mirrors this; plan v2 deviation 5's amendment records it; enhanced-mode plan Step 7 carries the code-side revision.

**ADR \#31 Title: Block Screen Parity — BlockerActivity Is the URL Pause Card's Twin; the Recovery Tab Owns Every Unlock**

**Status:** Accepted; implementation complete + device-verified 2026-09-13 (user-directed: one block language across app and URL blocks).
**Context:** The app block screen (blocking-core plan §8.1) carried its own block design, including its own countdown/override flow on the screen, while the URL path had just shipped the pause card (ADR #29/#30). Two surfaces, two languages for the same event; the user directed one: the block screen becomes the card's twin and the Recovery tab owns the friction UI for both block types. (4) **Tapjacking** (from ADR #28) stays: `filterTouchesWhenObscured` on the whole window. (5) **Unlock paths collapse to one call site.** The spent-session bypass is fixed by consuming the session in every unlock path — `RecoveryStateStore.clear()` called from `ui/recovery.unlockRule`; since the Recovery tab owns every unlock, that single call site is the whole class of paths (regression guard `RecoveryUnlockTest` fails if `unlockRule` stops clearing). **Verification:** Unit suite green (including `RecoveryUnlockTest`); lint zero. **ADR \#39 Title: Daily Usage Limits End-to-End (V1 Req 4/5) — Single-Transaction Accounting Engine, Two Detection Paths Under One Authority, Overlay-As-The-Block, and the Expiry Contract**

**Status:** Accepted; implemented (plan v2 Steps 1–11); device-verified on the X6532 (XOS 14) and the stock-Android emulator; gate green 2026-09-16 (487 JVM tests / 0 failures, lint zero). Authoritative spec: `app/plans/daily-usage-limit-enforcement-implementation-plan-v2.md` — this ADR records the decision set, the plan holds the detail.

**Context:** V1's daily limit was a dead branch — schema column + engine comparison existed, nothing fed usage (recorded 2026-09-13, un-deferred the same day by user direction). The v1 design's accounting premise (elapsed time between accessibility events; `UsageStatsManager` polling as a drop-in) was invalid: neither is a duration measurement. The rebuild had to answer three things at once — how usage is measured (sessions, not polls), who owns measurement when both a11y and the FGS are alive (exactly one), and how warnings/blocks surface without v1's overlay-vs-eviction race.

**Decision:** (1) **One transactional accounting cycle.** `UsageAccountingEngine.processUsageObservation(pkg, incrementMs, nowElapsedRealtimeMs)` — single Room `@Transaction` under one shared serialized dispatcher: read rule + tracker row → roll the day over if the stored `(local date, IANA zone)` anchor no longer matches (Decision 20: any mismatch rolls, including timezone moves) → accumulate → evaluate cached thresholds → persist → return `NoAction`/`ShowWarning(n)`/`Block`. Threshold pair = `limit−10min / limit−5min` at ≥10 min, else `50% / 90%`; recomputed only on limit change (`onDailyLimitChanged`, Decision 15) so a mid-day raise unblocks and re-derives. Warnings are a persisted state machine with retry — an undelivered level retries on the next observation (Decision 14). Non-positive limit means already-at-limit. All duration math is `elapsedRealtime()`-only (NFR3); wall clock is display + calendar identity only. (2) **Two detection paths, one authority.** Path A = `BlockerAccessibilityService` session machine + 10 s ticker (sessions open on window-state transitions, boot-count mismatch discards the session rather than crediting a stale delta, connect-time re-acquire for the pre-bound-foreground gap); Path B = `EnforcementForegroundService`'s existing 1.5 s `queryEvents` poll feeding sessions with an adaptive cadence (30 s baseline, 5 s under 3 min of budget; the plan's separate 30 s discovery loop was folded into that poll — recorded deviation). `ProtectionStatusMonitor` is the single writer of authority: FULL / DEGRADED_POLLING_ONLY / DEGRADED_NO_DETECTION, recomputed on cold start, post-unlock, maintenance runs, the FGS permission cadence, and a11y connect/disconnect; only the authority holder credits usage and renders the wall. (3) **The overlay is the block.** Path A renders through `OverlayController` (shared cover content) with attach-confirmed `GLOBAL_ACTION_HOME` eviction; Path B's wall is a bare `TYPE_APPLICATION_OVERLAY` view added directly to the window manager, reusing the device-verified ADR #30–#36 overlay content rather than the plan's Compose hosts (recorded deviation; same shared-content model). No `BlockerActivity` launch on the Path B path. Blocked-state re-arms on every subsequent observation, so re-entry re-walls without relying on the first overlay surviving. (4) **Warnings are non-modal banners** (`FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL`, 5 s or tap) so they never block the app they warn about; both surfaces consume insets explicitly. (5) **Maintenance is bookkeeping only.** `DailyMaintenanceWorker` (WM, daily, first run pinned to next 00:05) runs `rolloverStaleDays()` + status refresh — correctness never depends on it (Decision 5); rollover is guaranteed inside every accounting transaction. WM is deliberately excluded from timing-critical work (no `AlarmManager`, no WM-driven rollover). (6) **The contract: "tracked" = enabled *and non-expired*.** An expired rule (`isExpiredAt`) is invisible to the snapshot build and to both engine lookups — no accrual, no warnings, no wall — matching what the Rules row already claimed.

**Verification:** §12 lifecycle legs (rollover, concurrency, mid-day change, force-stop, revocation mid-session, A↔B handoff both directions, reboot) PASS; short-limit matrices complete on both paths on the X6532 (Path A all 8 rows, Path B all 8 rows under `DEGRADED_POLLING_ONLY`); §11 measured (Path A reopen P50 154 ms / P95 237 ms; Path B P50 808 ms / P95 914 ms; continuous loop 0.70–0.79% of a core vs the <2% NFR); emulator execution leg PASS (real WM dispatch + stock-Android wall render); regression pass on both devices with findings #1–#5 fixed and device-verified 2026-09-16. Defects found and fixed along the way (all device-caught, all recorded in the plan's step notes): Path B render gate dropping tick-originated verdicts (foreground carry-forward), Path A `onDestroy` dropping the session tail, Path B failing to re-acquire an already-foreground app after authority flip, missing `androidx.hilt:hilt-compiler` on the KSP classpath (every `@HiltWorker` failed to instantiate on stock Android — masked on XOS because no WM job ever runs there), XOS wall bounds computed from animating-task insets (settle re-run), and the expired-rule tracking leak.

**Trade-off Accepted:** (a) View-based overlay content instead of the plan's Compose hosts (reuse of the device-verified overlay system beat plan-literal wording). (b) Path B's poll-derived window (1.5 s grid) can miss launcher sojourns under ~1.5–2 s — an accepted measurement floor, recorded as OQ3 data, not a defect. (c) The documented ≤30 s under-count on a reverse authority handoff (favouring under-credit over double-credit). (d) `SYSTEM_ALERT_WINDOW` is required on every OEM for Path B's wall, not just Transsion (the ADR #30 exception generalized). (e) Path B's render path needs a live foreground observation; a tick that cannot see one drops the verdict rather than rendering blind.

**Consequences:** Daily limits are real end-to-end: set in the editor, accrued by whichever path holds authority, warned twice with retry, walled at the limit, re-armed on re-entry, rolled over transactionally, and reset mid-day on a limit change — with the wall, the banner, and the row state all agreeing on what "tracked" means. **ADR \#40 Title: Home-Screen Widget (V1 Req 36) — Materialized Snapshot, Three-Valued Honesty, and a Composition That Observes Instead of Re-Renders**

**Status:** Accepted; implemented 2026-09-16. Authoritative spec: `app/plans/desert-dawn-widget-phase6-full-spec.md` — this ADR records the decisions, the deviations, and what the plan asked for that the platform does not actually allow.

**Context:** Req 36's widget is the most exposed surface the app has: it renders on a home screen anyone can see, from state the app may no longer be able to vouch for. Two forces pull against each other. A widget host caches the last `RemoteViews` it was handed and may keep showing it indefinitely, so the app can never promise what pixels a launcher displays (spec §1). And a false "Protected" is the worst output this feature can produce — worse than no widget at all — because it is precisely the assurance the user is relying on. The plan answered with a governing rule (never render PROTECTED from a sample that is not confirmably fresh, correctly clocked, and valid since the last reboot) plus integration points; implementing it against glance-appwidget 1.1.1's real semantics required deciding four things the plan left open.

**Decision:** (1) **The widget renders a materialized snapshot and evaluates nothing.** `ProtectionSnapshotWriter` is the sole writer: it collects `ProtectionStatusMonitor.authority`, collects `HabitRepository.state`, and runs a 5-minute heartbeat, writing to a Preferences DataStore (`widget_protection_snapshot`) only when something moved or the stored sample aged past 10 minutes (`shouldRestamp`) — then calls `updateAll()`. Change-gated so a 30-second arbiter cycle does not re-render a widget nothing changed; heartbeat-driven so the stored age can never approach the ceiling the render path enforces. (2) **Three-valued honesty in one pure function.** `displayedStatusFor(snapshot, nowUtc, nowElapsed, nowBootCount)` takes every clock as an argument, so skew and reboot cases are unit-testable instead of device-only. The gate: absent or damaged snapshot → UNVERIFIED; boot-count mismatch → UNVERIFIED (a pre-reboot timestamp proves nothing about this boot); a wall-clock delta disagreeing with the monotonic delta by more than 5 minutes, or a wall-clock age past 30 minutes → UNVERIFIED; otherwise the enforcement tri-state decides. Enforcement is a tri-state (ACTIVE / INACTIVE / UNKNOWN) because "I cannot tell" must never render as "protection is off" (FR3a), and the mapping onto it was **user-ruled 2026-09-16**: `ProtectionAuthority` collapses to ACTIVE for both FULL and DEGRADED_POLLING_ONLY (blocks genuinely run on the polling path, and UNVERIFIED there would tell a user with working blocks that something is broken), INACTIVE only for DEGRADED_NO_DETECTION. The spec's two-field `policy` × `enforcement` matrix has no separate carrier: the arbiter already folds "the master switch is off" into DEGRADED_NO_DETECTION, which is the plan's `policy=INACTIVE → UNPROTECTED` row, so one tri-state replaces two booleans plus their combination matrix. Related: Req 36's draft content named `BlockDecisionEngine.blocksNow` as the status source, but `blocksNow` is a per-rule query with no enforcement concept — spec §16 Q2 asked this question and `ProtectionStatusMonitor.authority` is the answer. (3) **`provideContent` is called once per session; the composition observes the store.** The plan's §8 Step 3 called `updateAppWidgetState` + `provideContent` inside a `collect {}` loop. Verified against the 1.1.1 sources: `ContentReceiver.provideContent` returns `Nothing`, suspends until session shutdown, and a concurrent second call *cancels* the first — the loop would have hung on the first emission and cancelled itself on the second. The shipped shape calls `provideContent` exactly once and puts `collectAsState()` (initialized from an IO pre-read so the first frame is real content) inside the composition, with `.flowOn(Dispatchers.IO)` so the `Settings.Global` binder read the plan placed in that lambda never runs on the main thread. `updateAppWidgetState`/`PreferencesGlanceStateDefinition` are dropped as a second source of truth the global store already covers. (4) **Discreet copy is the default and the setting lives with the snapshot.** `WidgetSettings` (app-level) is mirrored into the snapshot by the same writer, so "what causes a widget refresh" stays one auditable list; the Settings toggle calls the writer's `publish()` directly. Copy is discreet by default: day count only, no status word, no recovery vocabulary (FR5).

**Verification:** Unit suite added and green (`:app:testDebugUnitTest --tests "com.example.myexodus.widget.*"`): the freshness/skew/reboot/tri-state matrix (`DisplayedStatusTest`), the restamp gate plus authority→enforcement mapping (`ProtectionSnapshotWriterTest`), the codec's fail-closed decode (`WidgetSnapshotTest` — unparseable or absent enforcement is UNKNOWN, absent discreet is discreet). **ADR \#41 Title: Partner Pillar v2 Pairing Registration — Token-as-Transport Rendezvous, Server-Authoritative `/pairings`, and the Two-Id Model**

**Status:** Accepted; implemented 2026-09-18 (client + Cloud Function + tests). The v2 rules file (Step 1, amended in Step 3 with the token single-use gate) is **written but not deployed** — deployment follows the client migration (Steps 9/10) and is a user step; the `registerPairing` function deploy (`firebase deploy --only functions`, Blaze) is likewise pending. Authoritative spec: `app/plans/partner-pillar-implementation-plan-v2.md` (§7 Steps 1–3, §8 Step 3, AD-02/AD-17a/b/AD-20a). Adopts wholesale by plan authority — safe because no pairing UI has ever shipped, so no production pairs exist and there is no data to migrate.

**Context:** v2 replaces the v1 pairing exchange (client-written `pairs/{pairId}` state, verified by two independent UID claims from the members map) with a server-authoritative `/pairings/{pairId}` record written **only** by the `registerPairing` Cloud Function, which activates it only when both devices' signed proofs arrive within a 5-minute window and carry matching `transcriptHash` values. Mailbox writes are then authorized against that record (AD-02). Two realities forced decisions the plan left open: a real Android attestation chain (~5 KB) overflows the QR ceiling (2953 B, recorded on-device 2026-08-30), so some rendezvous channel must carry the payload; and the plan's model dropped `pairing_tokens` entirely, which would have left no way to transport that payload.

**Decision:** (1) **The token document is transport only; authority is the signed proof.** `pairing_tokens/{sha256(token)}` carries the initiator's enrollment payload to the partner and the partner's response back (user-ruled: keep the token rendezvous — QR cannot carry attestation). Nothing in the token document grants authority — `/pairings` (function-written) does. The client's `PairingExchange` was rewritten to this shape (`registerToken` / `readToken` / `respondOnToken` / `pollTokenResponse` / `awaitPairingActivation` / `deleteToken`); the v1 `redeem` / `confirmPairing` / `pollPairState` are deleted, and `deletePairState` survives only for `BilateralDeletion` until the Step 14 unpair rework. (2) **Two ids, deliberately distinct.** The *session id* is the token's random per-attempt id: it binds the transcript, and therefore the SAS and the ceremony CEK, and dies with the attempt. The *durable pair id* is `min(uidA,uidB)+"_"+max(uidA,uidB)` (AD-02), computed independently on both devices (`EnrollmentTranscript.durablePairIdOf`) and by the function (`pairIdOf`) — it keys `/pairings`, the mailboxes, and `EnrollmentRecord`. Consequence to keep in mind: event-time envelope CEK re-derives from the **durable** pairId on both sides (`EventCreator` / `FirestoreMailboxReceiver`, unchanged), while the ceremony derives its CEK from the session id and persists only `derivePairingKey(ceremonyCek)` into `SecretsRepository` — the two values need not match, and nothing reads the stored pairing key yet; if a future feature (sealed backup, etc.) expects them equal, that is the point to revisit. (3) **Single-use partner response is a rules-layer property, not a transaction.** The `pairing_tokens` update rule carries `!('partnerUid' in resource.data)`: the first response commits, a concurrent second is denied at evaluation time, and the client maps that denial to `TokenAlreadyUsed` (`respondOnToken` catches `PERMISSION_DENIED`). No client-side transaction or read-check race exists to lose. The update rule also pins `creatorUid` / `expiresAt` / `payload` to their existing values and requires `partnerUid == request.auth.uid`, so a response can never impersonate or mutate the initiator's material. (4) **The function trusts only the proof, and the proof is canonical in two languages.** The signed message is `MyExodus-Pairing-Proof-v1 \n protocolVersion \n ownUid \n partnerUid \n publicKeyHash \n transcriptHash` — `functions/proof.js` and `PairingProof.canonicalMessageOf` assert the same literal in their own test suites. `protocolVersion` is inside the signed payload (an unsigned version field would allow a downgrade claim), and `signingPublicKey` (SPKI DER, base64) travels with the proof because the plan's field list omitted it while `publicKeyHash` binds it. Trust moved server-side: the **initiator's** transcript signature is now verified by the function (it is the pairing proof), which deleted `EnrollmentFlow.verifyTranscriptSignature`; the partner still verifies the initiator's **hardware identity** (attestation) locally before responding, and the initiator still verifies the partner's **full material** (attestation + transcript signature) before the SAS is displayed — §3's device-to-device check is unchanged. (5) **The client's create contract equals the rules' `hasOnly` exactly.** `pairingTokenData` emits `{creatorUid, expiresAt, payload}` and nothing else — `expiresAt` is a Firestore `Timestamp` so the rules can compare it to `request.time` (an epoch number would not be comparable in rules). A test pins the key set, because an extra field here would fail every token create in production with `PERMISSION_DENIED`. (6) **Region is locked to us-central1 across the stack** (AD-17b): the Firestore database, the callable, and the DI initializer (`FirebaseFunctions.getInstance(PairingRegistration.REGION)`). Verified in the artifact as a side-note: the KTX `Firebase.functions()` extension does not exist in `firebase-functions` 22.1.1 (BoM 34.18.0) — the Java static initializer is the correct call, not a style choice.

**Verification:** `functions/` node suite 5/5 (`npm test` → bare `node --test`; the directory-arg form fails on Node 22.17.1 with `MODULE_NOT_FOUND`) covering the canonical-message literal, valid/tampered/wrong-key signature cases, and stable structural reason codes. JVM unit suite 522 green (2026-09-18): `PairingFlowTest` rewritten to v2 fakes that mirror `functions/index.js` + `proof.js` (10 scenarios — full round trip landing the AD-02 durable pairId on both devices with identical SAS + pairing key + token deletion, expiry, single-use by pre-existing response, single-use by write denial, corrupt partner payload, corrupt partner transcript signature, function `TRANSCRIPT_MISMATCH` leaving the record pending and writing no `EnrollmentRecord`, partner registration lost → initiator signs into a pending record and aborts, QR session-id mismatch rejected pre-relay, poll timeout); new `PairingProofTest` (cross-language literal + the two rules `proof.js` enforces); `FirestoreSchemaTest` pins the create contract. `firestore.rules` loads clean in the emulator (`firebase emulators:exec --only firestore --project demo-myexodus` → `RULES_LOAD_OK`) after the single-use gate was added; behavioural rules-emulator tests are plan §12 scope, i.e. Step 20. Lockfile regenerated for `firebase-functions`; `assembleDebug` + lint run alongside this record.

**Trade-off Accepted:** (a) **The token rendezvous survives** even though the plan's model dropped it (user-ruled: the QR cannot carry the attestation payload, and the function-side proof model needs no token at all — the token is a payload shuttle). Cost: one extra rules-governed collection in the pairing path; benefit: no unauthenticated 5 KB QR requirement that the platform cannot meet. (b) **No client-side re-verification of the initiator's proof** — the partner relies on the function's verification, per the plan's server-authority model; the partner never needs the initiator's public key hash locally. The initiator, whose SAS gate depends on the partner's material, verifies locally (unchanged) — the asymmetry is deliberate. (c) **The v1 `pairs` / `deleted_pairs` helpers stay** in `FirestoreSchema` and `PairingExchange.deletePairState` until Step 14 reworks unpair, keeping each plan step build-green; the v2 rules already deny the v1 collections, so nothing new can be written to them. (d) **Activation-wait asymmetry**: the initiator waits 30 s for the partner's proof after its own registers as pending (a straggler window), while the partner may wait the full token TTL — the initiator only reaches that branch after a human SAS comparison, and the function's 5-minute window remains the real bound (reported as `Pending`).

**Consequences:** Enrollment now requires network reachability to the function and the Firestore database in us-central1 — the "recover the old pairing" path never existed, and a re-pair after any abort is simply a fresh token and a fresh session. A pairing attempt that dies between the partner's token response and its proof submission leaves a pending `/pairings` record (no authority) and a consumed token — the retry is a fresh attempt, and the function's `pendingSince` window plus `pairingEpoch` accounting keep the abandoned record inert. Deployment order is strict and staged: client migration (Steps 9/10) → rules → function; deploying the function before the client means dead code, deploying the rules before the client breaks the still-v1 write path (no production pairs exist, so the blast radius is the test device only).

**ADR \#42 Title: AD-23's SOS Per-Pair Threshold Dropped — the Mailbox Relay Stays Content-Blind; Volume Windows Are the Server-Side Enforcement**

**Status:** Accepted (user ruling 2026-09-18); implemented in `functions/relay.js` + `functions/relay-logic.js`. Deviates from the plan's AD-23 text (which names 5 SOS events per pair per hour as the third threshold).

**Context:** AD-23's mailbox rate limits are enforced in the relay before any push dispatch. Two of its three thresholds are volume windows the relay can count without reading anything: 10 events per pair per minute and 200 messages per sender per day. The third — 5 SOS events per pair per hour — is only countable if the relay can tell which messages are SOS. It cannot: the mailbox field contract (`senderId, senderUid, pairId, payload, keyEpoch, timestamp`) has no event type, and the payload is an end-to-end-encrypted envelope — the relay is content-blind by design (NFR2; the same posture that keeps push payloads to a generic wake signal, AD-11). The plan's own data sketch (`/rate-limits/{pairId}` mentioning `sosCount`) is internally inconsistent with its field contract; the gap was flagged during Step 5 and resolved by the project owner before the mailbox contract was deployed or the client write path was built.

**Decision:** Drop the SOS-specific server-side threshold. The 10/pair/min + 200/sender/day windows are the server-side abuse bound; SOS-specific pacing remains the client-side cooldown (§8 Step 12b) as the accident control, exactly the UX-layer role the plan already assigned it. The relay does not gain a type field and stays byte-blind.

**Alternatives considered:** (a) Add a cleartext `type: "sos"|"event"` to the mailbox contract (rules `hasOnly`, client sync worker, relay window) — enforces AD-23 literally and was cheap to do pre-deploy, but permanently labels the most sensitive event type to the untrusted relay, and is spoofable anyway (client-declared, unverifiable against ciphertext — a hostile client would simply lie and land back under the volume bound). (b) Enforce SOS pacing via a separate mailbox path — same labeling problem, worse (leaks by path). (c) Trim the payload — no content-blind mechanism exists on the roadmap, so any server-side SOS count is a labeling scheme in disguise.

**Verification:** `functions/relay.js` `checkAndIncrementRateLimit` counts exactly the two volume windows in one transaction; `functions/test/relay-logic.test.js` pins the window constants (10/60s, 200/24h) and window-state behavior. The decision is recorded in the function's KDoc at the enforcement site.

**Trade-off Accepted:** A compromised client can fire SOS up to the pair/minute volume bound (10/min) rather than 5/hour. This is accepted because the volume window already caps the flood, the harmed party (the partner) can unpair, and the alternative buys the tighter cap at the price of disclosing which messages are SOS to the server — an irreversible privacy regression on the app's most sensitive event class.

**Consequences:** If server-side SOS pacing is ever genuinely required, it must arrive as a content-blind mechanism (e.g., a server-verifiable pacing token), not as a cleartext label — re-opening this ADR requires that design first. The `/rate-limits/{pairId}` document therefore carries `pair` + `senders` windows only, not `sosCount`; monitoring (Step 19) alerts on the pair window instead.

**ADR \#44 Title: Mailbox Receive-Path Semantics — In-Transaction Dedup, Ack-on-Consumed, Marker-Free Deleted-Messages Reconciliation**

**Status:** Accepted; implemented 2026-09-18 (client). Deviates from the plan's §8 "Step 9" pseudo-code at three points (marker placement, ack gating, `onDeletedMessages` flag) — each deviation is visible in the code and pinned by tests. Cross-step contract for Steps 11 (chain repair), 14 (unpair), 19 (monitoring). Authoritative spec: `app/plans/partner-pillar-implementation-plan-v2.md` §6 step 7, §8 Step 9, §9 rows 2–3, AD-10b, AD-11b, AD-18b.

**Context:** The plan's receive pseudo-code sequences three separate effects — `commitToRoom()`, `ProcessedEvents.insert(messageId)`, `writeAck(messageId)` — and gates ack + notification on the `OK` outcome only; `onDeletedMessages()` sets a `sync_required` flag and "triggers" reconciliation. Three realities forced the shipped shape: (1) commit and marker as separate steps leave a crash window that either double-processes on retry or loses the marker — the exact failure AD-10b exists to prevent; (2) delivery is at-least-once (FCM redelivery + the watermark re-read), so `Duplicate` and `Gap` arrivals are *normal traffic*, and under AD-18b's "all registered non-stale installations have acked" cleanup condition an unacked duplicate pins a mailbox doc to the 30-day cap for no security benefit; (3) every pull already queries from the watermark, so a persisted `sync_required` flag would only ever be read by the pass that sets it.

**Decision:** (1) **Dedup inside the transaction.** `ChainStateStore.receiveRemote(pairId, envelope, messageId, at)` commits the chain append and the `processed_events` marker in ONE write transaction, and a seen `messageId` short-circuits *before any validation* — a conflicting envelope under a seen id is a plain `Duplicate`, never a fork (pinned by test). The handler additionally checks `processed` BEFORE the fetch (the plan's own ordering), so the transaction check is the crash-window backstop and the pre-fetch check is the network-saving gate. (2) **Mark consumed outcomes only:** `PROCESSED_OUTCOMES = {Appended, Duplicate, Gap}`. `Fork` and `Rejected` are not incorporated — no marker, so a re-delivery re-validates rather than being buried as processed (pinned by test). (3) **Ack on every consumed outcome**, not just `OK`: `{Appended, Duplicate, Gap}` are acked; `{Fork, Rejected}` and every non-Valid result are not (a re-delivery must re-validate or re-fetch). The ack (AD-18b subcollection, `installationId`-keyed) doubles as the §11 T4 app-level acknowledgment record — OQ-6 keeps it optional in V1, and the acks collection is the aggregation source Step 19 will read. (4) **No persisted `sync_required` flag:** `onDeletedMessages()` enqueues the same one-shot full pass the wake path uses; since every pull reconciles from the watermark, the pass *is* the reconciliation — AD-11b's requirement is served by triggering it, not by recording it. (5) **The wake work keeps a distinct unique name** (`partner-sync-wake`, KEEP) from the periodic worker (`partner-sync`): sharing a name would let a wake be KEEP-collapsed into a pass whose query had already passed the watermark point — precisely the loss the expedited path exists to prevent. Known ceiling: rapid successive wakes can collapse under KEEP, so a dropped wake's message lands via the running pass's bulk query or the next 15-minute run — latency-bounded, never loss, because the mailbox (not the push) is the source of truth. Two defensive additions the pseudo-code lacks: an own-`senderId` skip after the fetch (a replay of one's own message should not fail signature verification confusingly), and payload-decode failure as a logged no-op. The plan's `UNKNOWN_KEY_EPOCH` and `PROTOCOL_MISMATCH` branches are unreachable today and deliberately not coded: there is a single CEK until Step 15's epoch machinery, and `UnsignedEnvelope` carries no protocol version field — adding one would change the signed bytes, a wire-format change deferred until a version actually needs distinguishing.

**Verification:** `MailboxMessageHandlerTest` (11 cases pin the ordering and the side-effect fan-out: dedup before fetch — the load lambda never runs for a seen id; missing-doc no-op; own-sender skip; missing/malformed payload; invalid signature logged-unacked-unmarked; corrupt; appended → ack+notify exactly once carrying the transaction timestamp; duplicate+gap acked-but-never-notified; fork+rejected unacked; ack/notify failures never escape; deletion payloadType preserved on consumed outcomes). `ChainStateStoreTest` +2 (short-circuit-before-validation on a conflicting envelope; markers set for Appended/Gap only — Fork stays re-validating). `FirestoreSchemaTest` +1 (ack key set is exactly `{ackedAt}`). `PartnerSyncCoordinatorTest` +1 (wake messageId forwarded into the pull). Full unit suite 559/0/0/0 (80 classes; +15 this step). Device leg deferred: mailbox reads/writes are rules-denied until the v2 rules deploy.

**Trade-off Accepted:** (a) **Ack loosens from "newly applied" to "consumed"** — a consumer that wants "events applied" must read chain rows, not acks; the acks collection answers "did this device consume this message", which is what AD-18b cleanup and T4 need. (b) **A forked message is re-fetched on every wake until the 30-day cleanup deletes it** — bounded cost, and the correct behavior: a fork must stay visible to the repair/staleness path. (c) **One redundant dedup lookup per message** (pre-fetch + in-transaction) in exchange for never paying a network fetch on a duplicate. (d) The `SELF` skip is evaluated after the fetch (it needs the doc's `senderId`), so an own-message replay still costs one read; the alternative — comparing before load — is impossible since the sender id *is* the doc content.

**Consequences:** Steps 11 and 19 now have a stable three-way contract: acks = consumed (any outcome), `processed_events` = incorporated-or-held (Appended/Duplicate/Gap), chain rows = applied state. Step 11's repair builds on the Gap branch: the held row is already in the chain table (PENDING_GAP) and already marked, so the repair request is an *addition* to the Gap outcome, not a rework; the existing `gapSequences`/`expireGaps` (7-day pending window) stay the local half. **Revision 2026-09-18 (Step 11):** the `expireGaps`/7-day-window clause is superseded — Step 11 (ADR #45) deleted `expireGaps` (it had zero production callers) and replaced the local 7-day terminal with AD-08's 30-day staged repair. Step 14's unpair needs no new clearing — `deletePairData` already removes chain rows, outbox, and (via the same transaction discipline) can extend to `processed_events` if the pair is ever re-created with recycled message ids (it cannot today: message ids are per-event UUIDs). If the wire format ever gains a protocol-version field, the `PROTOCOL_MISMATCH` branch lands in `MailboxMessageHandler` with the other envelope gatekeepers.

**ADR \#45 Title: Chain Repair Protocol (AD-08 staged) — Repair-Request-as-Ordinary-Event, Anchor-Proof Responder, and the v1 Backfill Retirement**

**Status:** Accepted; implemented 2026-09-18 (client; unit-verified). Supersedes the `expireGaps`/7-day-pending-window half of ADR #44's Consequences. Authoritative spec: `app/plans/partner-pillar-implementation-plan-v2.md` §7 item 11, §8 Step 10 (five points), AD-08/AD-08b (lines 176/178), §9 rows 456–458, §12 lines 524–525, §14 line 574, acceptance 625–626.

**Context:** A chain gap had two local half-measures — `PENDING_GAP` buffering and a 7-day `expireGaps` sweep that nothing in production called — plus a v1 reverse channel (`backfill_requests` documents + `FirestoreRelay.respondToBackfillRequests`) that re-sent stored bytes for missing sequences. The v2 plan replaces both with a staged repair: a gap must never be declared permanently unrecoverable immediately (the partner may just be offline), and the replay must be *provable* against the exact chain link, not merely the sequence number. The plan also reserves `TAMPER_SUSPECTED` exclusively for a supplied replay that fails signature or hash verification — never for benign missing history.

**Decision:** (1) **Three-stage terminal path, one stage per pass.** `NONE → REPAIR_PENDING → RECOVERY_EXHAUSTED → CHAIN_INCOMPLETE`, carried by three new `chain_heads` columns (`repair_state`, `repair_first_requested_at`, `repair_last_requested_at`; DB v6). Stage 1 opens in the *same transaction* as the buffered orphan (no pass can observe a gap without its marker); a head with no gap buffered cannot start a repair, and an exhausted/terminal head never restarts (a new orphan in a lapsed namespace stays terminal). Stage 2 lands when the 30-day window (anchored on the first request, not the last) lapses with the gap still open; stage 3 one pass later. Splitting the escalation across passes makes `RECOVERY_EXHAUSTED` observably persisted and gives a late replay a natural grace period to heal from — a replay that closes every gap resets the head to `NONE` and clears both timestamps inside the cascade transaction. (2) **The SyncRequest is an ordinary signed chain event** in the *requester's own* chain (`TYPE_SYNC_REQUEST` + two absent-when-unset CBOR fields `ps`/`ph`), so it travels the existing outbox → mailbox → verify-decrypt-append pipeline with no parallel transport; one per 24h per repairing head, created only while the biometric window is warm (a cold window defers to the next pass — never prompts from background). `expectedPreviousSequence`/`expectedPreviousHash` are the requester's stored *partner-namespace head*: the last partner event it actually holds. (3) **The responder proves connection (AD-08b), not sequence arithmetic.** `respondToRequest` hash-matches the requested anchor against this device's own stored event at that exact sequence; on mismatch it replays nothing ("histories diverged" — no replay can honestly fix it). On match it re-enqueues the stored bytes after the anchor with fresh messageIds (same eventId, capped at `REPLAY_BATCH_LIMIT = 100`; the daily re-request covers the remainder). (4) **Tamper correlation via the repair state.** Replays are byte-identical re-sends, so an active repair is the only discriminator between a tampered replay and ordinary noise: a signature failure during an active repair (`MailboxMessageHandler` → `flagTamperIfRepairing`, pair-level) and a hash-verification fork during an active repair (`flagFork`, head-level) both set `TAMPER_SUSPECTED` + `forked=true` → automatic trust of that sender blocked (forked chains reject every append). Correlation set = `{REPAIR_PENDING, RECOVERY_EXHAUSTED}`; the terminal and tamper states are mutually exclusive and never conflated (§9 row 457 vs 458). (5) **v1 retirement, deliberately scoped.** `expireGaps` deleted; `SYNC_STATE_PERMANENTLY_INCOMPLETE` renamed to `SYNC_STATE_CHAIN_INCOMPLETE` (v6 migration UPDATEs any old rows); the whole v1 BACKFILL channel retired — receiver block, `FirestoreRelay.respondToBackfillRequests`, coordinator seam, DI wiring, `FirestoreSchema.backfillRequest*`. Left as a noted pre-v2 remainder: `FirestoreRelay.drainOutbox` + `EVENTS_COLLECTION` + the v1 `pairs` schema (firestore.rules still references them; retiring them is a rules+client change for a later step). Known boundary: a gap arriving with *no head yet* cannot be marked (AD-08b needs an attested head to anchor on) — it stays a plain `Gap` until the predecessor arrives and creates the head, documented in code and pinned by test.

**Verification:** `ChainStateStoreTest` +7 new repair cases (2 legacy expire tests removed): request bookkeeping anchors the window on the first request and advances the last; escalation reaches the neutral terminal with gap rows marked `CHAIN_INCOMPLETE` and `forked=false`; a late replay from `RECOVERY_EXHAUSTED` heals and clears both timestamps; a later orphan does not restart a lapsed repair; a conflicting event during repair is `TAMPER_SUSPECTED` + blocked; `flagTamperIfRepairing` true only while active; `enqueueReplay` re-queues exact bytes after the anchor with fresh ids + honors the limit. New `ChainRepairCoordinatorTest` (8 cases, real DB + real crypto): anchor carried on the request (decrypted and field-checked), 24h cadence, cold-window skip with retry, unpaired no-op, one-stage-per-pass escalation, heal-within-window closes the repair, responder match → exact bytes re-enqueued, mismatch → nothing. `AccountabilityDatabaseMigrationTest` +1 (v5→v6: repair columns default to `NONE`, `PERMANENTLY_INCOMPLETE` → `CHAIN_INCOMPLETE`) + `EnrollmentDaoTest` migration list extended. `EventPayloadTest` +2 (anchor fields round-trip; absent-when-unset byte stability). `MailboxMessageHandlerTest` +4 (sync-request answered + notification suppressed; anchorless request logged no-op; invalid signature during repair → `TAMPER_SUSPECTED`; without a repair → ordinary `BAD_SIGNATURE`). Full unit suite 577/0/0/0 (2 pre-existing test-only failures fixed: missing v6 in two migration lists; a test scenario that mis-linked the gapped event — the store behavior was correct). Device leg deferred: the repair round trip rides §12's Step 20 matrix after the v2 rules deploy.

**Trade-off Accepted:** (a) **One redundant SyncRequest per 24h per broken head until the window lapses** — keeps the ask visible without alert noise; the cost is one signed event/day, and the request itself is chain-bounded. (b) **The responder's replay drains on the *next* pass** (replays are enqueued during the pull's inline handler, after the drain step) — worst-case heal is bounded by the requester's daily re-request, which is the cadence the protocol already budgets. (c) **Escalation does not require fresh evidence of sender activity beyond the unhealed gap** — acceptance 625 defines the window on requests, and `gapSequences` non-empty *is* the same broken point persisting (any event before the break would have been absorbed by the cascade). (d) **`TAMPER_SUSPECTED` is a one-way door per sender** (`forked=true`) — recovery is manual re-pair; this is AD-08's stated intent and the conservative side of a security signal.

**Consequences:** §14 line 574's two counters now have distinct sources: `CHAIN_INCOMPLETE` (product/retention signal) reads terminal `repair_state` rows; `TAMPER_SUSPECTED` (security signal) reads `repair_state` + `forked` — Step 19 must track them separately. Step 12's dashboard owns §9 row 457's neutral copy ("some history could not be synced") for terminal heads. Step 15's key rotation reuses the same outbox replay mechanics; if an `UNKNOWN_KEY_EPOCH` branch ever lands, its responder-side twin belongs beside `respondToRequest`'s anchor check. The v1 `accountability_events` drain path and `/pairs` rules are the last pre-v2 remainders; retire them when firestore.rules drops their clauses.

**ADR \#46 Title: The Virtual-Partner Harness — §12's On-Device Round Trip Without a Second Attesting Device**

**Status:** Accepted; implemented 2026-09-18 (debug/androidTest sources only; no production code changed). Covers §12's "Chain repair" instrumented row, temporary-gap branch — the first on-device exercise of the full v2 pipeline. Exercises the deployed v2 rules + functions (relay, registerPairing) end to end. Authoritative spec: `app/plans/partner-pillar-implementation-plan-v2.md` §12 (instrumented + device-matrix rows), §13 (deploy gate), §7 items 3/7/9/10/11.

**Context:** §12 requires the pairing → send/receive → gap-repair path proven on a device before rollout, and §13 gates the deploy on it. Three routes are excluded by prior evidence: an emulator cannot attest (software keys fail the app's own PKIX pinning — proven 2026-09-16); running both roles on one device is dead under v2 (one keystore key for both roles → `registerPairing`'s `SAME_KEY` rejection); and no second physical attesting device exists in this project. The harness therefore has to produce two genuinely distinct, genuinely attested identities on one phone.

**Decision:** (1) **Virtual partner = second FirebaseApp + second attested keypair.** `PartnerTestIdentity` carries its own `FirebaseApp` ("partner-test": own anonymous uid, auth, Firestore, Functions transport) and its own hardware keypair under test-only aliases (`PartnerTestKeys`, TEE — not StrongBox, whose per-app slot budget cannot hold a second identity). Distinct `publicKeyHash` passes `SAME_KEY`; the chain is a real Google-rooted TEE attestation, so the device's unmodified `AttestationVerifier` accepts B exactly as a second phone's would. A fresh anonymous uid per run: the pair is always new, the pairing leg is exercised every run, and chain scenarios always start at sequence 0 (a persistent uid would hit `PAIRING_ACTIVE` on re-runs). The signing key persists across runs — the attestation challenge is read from the chain itself, not a per-session nonce, so re-verification succeeds. (2) **Every wire leg and protocol decision is production code.** A runs the app's real singletons via `RoundTripTestEntryPoint` (Hilt entry point: real `PairingFlow`, `AccountabilitySigner`, `ChainStateStore`, `PartnerSyncCoordinator`); B runs production `PairingFlow`, `EventCreator`, `ChainRepairCoordinator`, `MailboxOutboxDrainer` wired to the secondary transport. Real `registerPairing` both ways, real mailbox writes under the deployed v2 rules, real relay. (3) **B gets its own Room DB file** (`myexodus_partner_test.db`, wiped at construction). Learned on-device: the real DB keys everything by `(pairId, senderKeyId)`, so on a shared file B's *local* appends advance the very head A's receive path checks — A's receives all read as `Duplicate` and the deliberate gap never opens. Only two local fakes remain, both because the real ones belong to A: B's in-memory `EnrollmentDao` and a no-op `SecretsRepository`. (4) **No server pre-reads of possibly-invisible documents.** The v2 pairings read rule deliberately denies non-member reads (including a missing doc) as a probing guard; the production path already catches that denial and keeps polling (a "not yet registered" signal). The harness matches production: decide pairing from local state, never probe.

**Verification:** Instrumented run 2026-09-18 on the X6532, `OK (1 test)` in 23.1 s (`RESULT roundtrip=PASS`): real pairing completed with matching SAS on both roles (`Paired` ×2, SAS 17936); sync1 — A committed base+1..2 and opened `REPAIR_PENDING` with base+4 buffered as the gap row (`pulledCount=2`); sync2 — `repairRequestsCreated=1`, the SyncRequest drained through A's production outbox into B's mailbox; B's `respondToRequest` hash-matched the anchor and replayed exactly 2 events (byte-identical, fresh ids), drained by B's production drainer (`Sent(eventsDelivered=2)`); sync3 — the chain healed to base+4, `gapSequences` empty, `REPAIR_NONE`, `forked=false` (the §12 "neither path produces TAMPER_SUSPECTED" clause), and A's receive pipeline left acks (AD-18b leg). Requires one user biometric tap ("Warm signing window" in the debug `PairingTestActivity`) covering every signature in the run — the keystore's 900 s window is device-level, so one tap covers both identities.

**Trade-off Accepted:** (a) **Cross-device distinctness is not exercised** — the fiction is "two uids, one phone". Device-level behaviors that only exist across two physical devices (clock skew between attestors, independent relay delivery, Doze on the receiving device) remain uncovered until a second attesting device exists; the §18 rollback exercise has the same dependency. (b) **The exhaustion row and the tamper row stay unit-level** (`ChainStateStoreTest` raises `RECOVERY_EXHAUSTED` → `CHAIN_INCOMPLETE` with a real DB; the tamper path is pinned by the same suite and `ChainRepairCoordinatorTest`) — the exhaustion leg needs backdated repair bookkeeping that only a purpose-built harness or Step 20's matrix should fake. (c) **The harness ships in debug builds** (debug source set + androidTest APK) — never in release; the test-only keystore aliases are destroyed only by uninstall.

**Consequences:** §12's temporary-gap device row is satisfied; Step 20's device matrix should absorb this harness as a repeatable row and add the exhaustion variant (backdating the first-request timestamp) when the full suite runs. The harness is the template for any future two-identity device test (Dashboard/approval UI legs, unpair round trip): a second FirebaseApp + second attested alias + its own Room file, no protocol fakes. The failed pre-read also re-confirmed the rules' probing guard from the client side — a client that wants pair status must derive it from local state or catch the denial, never expect an "exists=false" answer.

**ADR \#47 Title: Partner Dashboard UI (Step 12) — Local-Only Read Model, Production Re-Decode of Stored Envelopes, and the Sixth Tab**

**Status:** Accepted; implemented 2026-09-18 (client; JVM suite + on-device leg green). Authoritative spec: plan v2 §7 item 12, FR3 (§9 rows 457–458 and 468, §11 line 502, acceptance line 631), AD-05.

**Context:** The dashboard is the partner pillar's first UI. The contract: last-known state with an explicit "last synced" timestamp (FR3); initial render from cached local state with ZERO network round-trip that never blocks paint (§11 line 502); distinct copy for the repair states (§9 rows 457–458 — the neutral CHAIN_INCOMPLETE reading vs the trust-blocking TAMPER_SUSPECTED one); a persistent banner with a settings deep link while notification permission is denied (§9 row 468 / acceptance 631); and AD-05 honesty — the copy never promises real-time delivery. Two realities shaped the implementation: (1) the activity text lives inside encrypted envelopes, so "blocked:/override:" rows can only be shown by re-running verify-then-decrypt over the *stored envelope bytes* — any cached plaintext copy would be a second, less trustworthy source; (2) XOS never dispatches WorkManager jobs at all (ADR #27), so a "Check now" that enqueued work would be a dead button on the test fleet's primary device — the production sync pass has to run in-process.

**Decision:** (1) **`PartnerDashboardSource` is the read model, local-only.** `load()` takes the latest enrollment (later re-pairs win), reads the last 7 days of stored received chain rows, re-decodes each row's envelope through a `decoderFor(EnrollmentRecord)` seam that DI wires to the production pipeline — `MailboxEventProcessor.process(partnerSigningKey, cek, envelope)` with the CEK derived exactly as `FirestoreMailboxReceiver` derives it (`decodePublicKey` was promoted from that receiver's private helper to a top-level `internal` so this is literally the same decoding code). A row that no longer verifies, or decodes to a non-activity payload, is skipped — never shown as something it is not. A key-material failure inside `decoderFor` (unreadable keystore entry, corrupt DER) degrades to "no decodable rows"; `receivedSince` failure degrades to empty activity — both still render Paired, neither strands the screen on Loading. Freshness is a property of the enrollment's mailbox watermark, never of this call. (2) **Presentation is pure functions** (`PartnerPresentation.kt`): `syncFreshness` NEVER/FRESH(1h)/AGING(24h)/STALE with future clock skew reading FRESH (an over-eager "delayed" warning is the dishonest direction); `relativeTime` buckets plus `Older(epochMillis)` for the screen's date rendering; `chainStatusFor` maps forked or `TAMPER_SUSPECTED` → UNVERIFIED, `ACTIVE_REPAIR_STATES` → CATCHING_UP, `CHAIN_INCOMPLETE` → INCOMPLETE, everything else (including an absent head — a fresh pairing with nothing received yet is not a problem state) → HEALTHY; `parseActivityText` accepts exactly the two EventCreator prefixes; `summarizeAlerts` counts "today" against start-of-local-day and caps the recent list at 5. (3) **Sixth tab.** "Partner" (Handshake icon) at index 4, Settings moved to 5; the label doubles as the deep-link key in the existing interception escape hatch. Six destinations is beyond Material's 3–5 nav-bar guidance, and at 360dp six labels physically cannot coexist — the bottom bar therefore shows labels on the selected item only (`alwaysShowLabel = false`, the platform's `LabelVisibilityMode.AUTO` behavior for 4+), while the expanded-width NavigationRail keeps full labels. (4) **"Check now" runs the production pass in-process** via the shared `runPartnerSyncPass(pushInstallationRegistrar, partnerSyncCoordinator)` helper the wake worker uses (registrar.register() + `syncOnce(wakeMessageId)`) — ADR #27's consequence, with the button's result alone deciding the "couldn't check" copy. (5) **Notification banner is live, not launch-time.** `NotificationAccess.canPost` is read at composition and re-read in the existing ON_RESUME observer (acceptance 631: the state must re-check when the user returns from settings); the deep link is `ACTION_APP_NOTIFICATION_SETTINGS` for this package. (6) `MainActivity` injects the dashboard source, the coordinator, and the registrar; nothing new persists.

**Verification:** JVM — new `PartnerPresentationTest` (10: freshness buckets incl. skew, relative-time buckets + Older, `chainStatusFor` all five repair states + forked, `parseActivityText` both kinds + non-activity null, `summarizeAlerts` today boundary + cap, `startOfLocalDay` against a fixed zone) and `PartnerDashboardSourceTest` (11: unpaired; latest-enrollment-wins; paired+healthy with decoded activity and the watermark read FRESH; never-synced; tamper-suspected and forked both UNVERIFIED; repair-pending CATCHING_UP and missing-head HEALTHY; undecodable rows skipped; decoder key-material failure degrades to empty; received-read failure still renders Paired; the 7-day window pinned via the `since` argument). Full unit suite 598/0/0 (was 577; +21). Device leg (X6532, 2026-09-18, through the ADR #46 virtual-partner harness): `PartnerDashboardInstrumentedTest` `OK (1 test)` in 18.6 s — a fresh virtual partner pairs, B emits `blocked:com.android.chrome` + `override:com.android.settings` through the production `EventCreator`, the production drainer delivers both (`Sent(eventsDelivered=2)`), A's `syncOnce` pulls 2, and the DI-wired `PartnerDashboardSource` — the exact source the tab renders — reads Paired / FRESH / HEALTHY with todayCount 2 and both targets decoded through the production pipeline (`RESULT dashboard=PASS keyId=dcee1e380ead… targets=[com.android.settings, com.android.chrome]`). **ADR \#48 Title: Approval UI + Epoch-Bound State Machine (Step 13) — Canonical Request Derivation, Server-Anchored Expiry, and the Two-Sided CAS**

**Status:** Accepted; implemented 2026-09-18 (client; unit-verified). Authoritative spec: `app/plans/partner-pillar-implementation-plan-v2.md` §7 item 13, §8 Step 12 (states + exactly-once guard), §6 line 240 (badge before approve/reject), §9 row 459, §10 line 624, §11 line 333 (response fields), AD-07, AD-16, AD-23 (line 224, context only).

**Context:** The disable-approval flow is the plan's one stateful control conversation: a requester chains a `TYPE_APPROVAL_REQUEST`, the partner's device records it, a human decides (biometric-gated), and the decision travels back as a `TYPE_APPROVAL_RESPONSE` that the requester applies — with a plan-mandated guarantee stack on top: exactly-once transitions (`WHERE status = 'REQUESTED'`), epoch-bound correlation that closes replay-after-re-pair (AD-07), a 72h expiry whose security-relevant enforcement is server-timestamp-anchored (AD-16), and a hash-chain verification badge in the responder's UI before either button is usable (§6 line 240). Three implementation realities shaped the design: (1) the request's event id must be *the same string* on both devices although each side only sees its own copy of the wire, (2) the two sides' clocks are independently manipulable, and (3) the decision gesture is a keystore signing operation (BiometricPrompt on a device key), so the flow must run as a suspend chain, not inside a Room transaction that could interleave with `EventCreator`'s own create mutex.

**Decision:** (1) **Canonical request id, never self-reported.** `requestEventId = "<senderKeyId>:<sequence>"` — derived on the responder from the *verified envelope's* chain position and on the requester from its own post-create chain head. The request payload deliberately does NOT carry its own id (deviation from a self-referential reading of line 333; strictly stronger: a sender cannot spoof its chain position, Step 11 replays preserve it, mailbox re-drains cannot forge a new one). The wire fields line 333 mandates are all present on the *response*: `requestEventId` (`rid`), `pairingEpoch` (`pe`), plus `decision` (`dec`). (2) **One `approval_requests` row per request on BOTH devices** (DB v7; `role = REQUESTER | RESPONDER`), plus `enrollments.pairing_epoch` (AD-07; migration backfills 0 = "pre-v7 enrollment", which can never match a live epoch). The epoch is threaded from the `registerPairing` response AND the `/pairings` doc through both halves of `PairingFlow` into the enrollment — all four finalize sites. (3) **Every transition is a single-statement CAS** (`ApprovalRequestDao`): `casDecide` (responder; carries `AND expires_at > :now` — the server-anchored deadline is authoritative at the instant of the one write), `casApply` (requester; NO expiry filter — the responder's server-anchored decision is the authority; the requester's clock only ever produced display state), `casRevert` (guarded on the decided status so a racing sweep or duplicate response is never clobbered back), `casExpireDue` (72h sweep, called from the sync pass via a new `PartnerSyncCoordinator` seam), `casConsume` (APPROVED → CONSUMED, the single-use boundary the Strict Mode gate will cross). `insertIgnore` (first writer wins) makes re-delivered requests no-ops — a re-delivery never re-notifies. (4) **AD-16 anchors, both directions.** The responder's deadline is anchored on the mailbox document's Firestore server timestamp (`onRequestAppended` receives it via the handler seam); the requester's is local wall clock, display-only. The responder refuses outright when `now < row.createdAt` (backward clock rollback must not resurrect or extend anything). (5) **CAS-decide first, then chain the response; revert on create failure.** Nesting `EventCreator.create` (and its create mutex) inside a DB transaction risks deadlock; instead the row moves first and a create that returns `Failed` triggers a status-guarded `casRevert` so the row and the wire can never disagree about whether a decision was sent. `Duplicate` create (identical bytes already chained) counts as delivered. (6) **Epoch checked three ways on apply** (row == response == current enrollment; any mismatch → logged, not applied — §9 row 459, §10 line 624), and on receive (payload epoch vs enrollment; mismatch → dropped silently, no row, no notification). (7) **UI: badge gates the buttons.** `PartnerScreen` renders pending RESPONDER rows as `ApprovalRequestCard` with the chain-verification badge (verified / verified-but-catching-up / blocked-untrusted) shown *before* the controls; Approve/Reject are enabled only when `chainStatus != UNVERIFIED` (CATCHING_UP responds with the caveat badge — the request itself was verified at append time; an event that fails verification never becomes a row). REQUESTER rows render as `MyRequestsCard` with status + expiry. The decision gesture is a `BiometricPrompt` in `MainActivity` (`FragmentActivity` base; two-path CryptoObject contract as proven on the X6532: initSign-wrapped when the keystore allows, else prompt-without-crypto and initSign inside the success callback — the 900 s window makes that valid), then `ApprovalFlow.respond`. Refused/cancelled leaves the request open — the honest state. (8) **`approval_requests` is its own HIGH-importance channel** (plan §8 Step 16's channel spec; tray copy generic per NFR2), and the generic partner-event notification now skips approval payload types — the flow owns its own two notifications. (9) **Requester creation UI deferred, deliberately.** The only product-valid caller of `requestApproval` is the Strict Mode disable gate; `PARTNER_APPROVAL_ENABLED` stays `false` — flipping it would make disabling strict/enhanced mode impossible on a single-device fleet (a real partner device is the precondition). Recorded as an open product decision, not silently implemented.

**Verification:** JVM (Robolectric, real Room + real crypto through the production `EventCreator`): new `ApprovalFlowTest` — 18 cases: request chains the event under the enrollment epoch and persists the REQUESTER row with the canonical id; not-enrolled; `onRequestAppended` inserts the server-anchored RESPONDER row (createdAt/expiresAt from the *server* timestamp, not the clock) and notifies exactly once across a re-delivery; wrong/missing epoch request dropped without a row; approve and reject move the row and chain an epoch-bound response (`rid`/`pe`/`dec` field-checked through decrypt); a second respond is refused and chains nothing; an expired row refuses at the CAS and chains nothing; wrong-epoch refuse; clock-rollback refuse; requester-row/unknown refuse; `applyResponse` applies + notifies, replay does not move a decided row again, epoch mismatch (payload vs row, row vs enrollment) both rejected untouched; consumed/expired rows rejected (§11 line 624); unknown/malformed dropped silently; `expireDue` expires exactly the past-deadline rows; `consume` is one-shot from APPROVED only. `AccountabilityDatabaseMigrationTest` +1 (v6→v7: `approval_requests` created and CAS-live, `pairing_epoch` backfilled to 0 with enrollment data intact; all three earlier cases extended through `MIGRATION_6_7`). `PairingFlowTest` updated for the epoch-carrying fakes. **Plan-fidelity note:** §12's only approval-mandated test is the JVM rejection trio (non-existent / consumed / wrong-epoch response) and §17's acceptance criterion is the same single item — both fully covered above. No instrumented or device test is required for this step; a device leg (two-device, X6532 ↔ emulator) was planned as belt-and-braces but is impossible as specified: `EnrollmentFlow` runs the PKIX-pinned attestation verifier on both halves and emulator software keys fail it (ADR #46 Context, proven 2026-09-16). If device evidence is wanted anyway, the ADR #46 virtual-partner harness (second TEE alias on the X6532) is the only working route.

**Trade-off Accepted:** (a) **The request does not self-report its id** — a literal reading of line 333 would have it echo `request_event_id`; the canonical derivation is strictly stronger (chain position is unforgeable) and is recorded here as the deliberate deviation. (b) **A crash between `casDecide` and the response-create leaves a locally-decided row with no wire event** — the revert only covers a create that *returns* `Failed`, not process death mid-call; blast radius is one stuck local row (no security effect; the partner's request stays open until its own 72h expiry). Accepted as a narrow window; a repair sweep would be the fix if it's ever observed. (c) **CATCHING_UP allows responding** (with the caveat badge) — blocking there would strand requests during any slow repair; only UNVERIFIED (forked/TAMPER_SUSPECTED) blocks, which is what §6 line 240's "hash-chain verification badge" is for. (d) **`consume()` ships with no production caller yet** — the Strict Mode gate is deferred behind the same un-flipped flag; the API and its CAS are tested so the gate lands as pure wiring.

**Consequences:** Step 14 (unpair) must extend `deletePairData` to the `approval_requests` rows (local shred completeness). Step 15's key rotation rides the existing envelope `keyEpoch`; approval correlation is sequence-based, so rotation does not touch it. Step 16 inherits a partially-done channel story: `approval_requests` is HIGH per spec; `partner_alerts` still needs its HIGH fix and `sync_status` (LOW) is still missing. Step 19's counters: requests/decisions/refusals ride the existing event counters; no new metric is needed. The ADR #46 harness is the template to extend with an approval leg when a second attesting identity is available (the emulator cannot attest — ADR #46 Context).

**ADR \#49 Title: Unpair Protocol + UI (Step 14) — Journal-First Ordering, Ack-as-Evidence, and Two Rules Amendments**

**Status:** Accepted; implemented 2026-09-19 (client + rules; JVM- and rules-emulator-verified). The two `firestore.rules` amendments were emulator-verified 2026-09-19 and **deployed 2026-09-19** (user approved; gate re-run 19/19 immediately before — task #33 closed). Authoritative spec: plan v2 §7 item 14 (line 261), §8 unpair protocol UI copy (line 429), AD-13a/b (lines 194–196), FR4 (line 51), §9 row 460, §12 line 526, §17 line 655, §10, AD-18b.

**Context:** Unpair is the one guarantee the system cannot fully provide, and the plan's honesty rules (FR4, AD-13b, §17 line 655) forbid pretending otherwise: local shred is guaranteed and unconditional; remote shred is acknowledgment-based and best-effort; `LOCAL_ONLY_TERMINATED` must never be conflated with `TERMINAL`, in state or in copy. Three implementation realities shaped the design. (1) **The shred destroys the data the delivery needs** — wiping the chain and enrollment removes the very outbox row and keys the request event was built from, so anything the initiation still needs after the wipe (request bytes, sender key id, key epoch, message id) must be journaled first. (2) **A crash must not skip the shred** — AD-13b's "unconditional" means the journal row, not the request event, is what later passes resume from; the row is written *before* the event exists, pinned to the message id the event will carry. (3) **"Their copy is gone" has exactly one honest source of evidence** — the partner device's own AD-18b ack on the request message. Delivery success, drain results, and timeouts are all local inferences and are never presented as erasure. A fourth discovery came from auditing: the v2 rules as shipped made the whole protocol *undeliverable* — `pairings` was `write: if false` (so `terminatePair` was silently impossible, Req 29 broken in production) and acks were readable only by the recipient (so the initiator could never see the partner's confirmation, making REMOTE_SHRED_CONFIRMED unreachable).

**Decision:** (1) **Journal-first ordering, both halves.** The initiator writes the `unpair_state` row (DB v8) before `EventCreator.create`; a create that returns `Failed` deletes the row and fails the tap cleanly — nothing journaled, nothing shredded. The responder (`handleIncoming`, wired from the mailbox receive path's `onDeletionRequest` seam after signature verification) journals first too, so a crash mid-shred still leaves an accurate record *and an owed ack*. (2) **The shred is unconditional once the request exists**: `destroyAgreementKey()` + `deletePairData` + enrollment delete + `markShredded`, regardless of every drain outcome; `shredIfPending` re-runs it on any later pass that finds a row whose flag never landed (ADR-13b crash repair; idempotent — one device-level key destroy + an idempotent pair wipe). `deletePairData` now also wipes `approval_requests` (the ADR #48 Consequences item — local shred completeness: a stale REQUESTED row must not outlive the partnership). (3) **Drain-before-shred, bounded.** Every pending outbox batch older than the request is drained first (the wipe would strand it forever), capped at `MAX_DRAIN_BATCHES = 40` (2× Req 27's 1000-event chain cap) so a lying drainer can't loop forever. (4) **The ack is the only remote evidence.** `resumeRequester` polls the partner's acks on the journaled message id *first* — an ack proves the partner processed the request no matter what the delivery bookkeeping believes (a crash between mailbox write and the SENT mark is indistinguishable from a denial). Only on ack: `markConfirmed` + TERMINAL. `resumeResponder` writes the ack only after the shred completed (it cannot over-claim) and retries it from the journal on later passes — the responder's enrollment is already gone, so nothing else would ever retry it. (5) **`resumePending` runs before the sync coordinator's enrollment early-return** (`resumeUnpairs = deletion::resumePending`, AccountabilityModule.kt:419): a post-shred device has no enrollment, yet its in-flight unpair is exactly what still needs network work. A shredded row with a live enrollment for the same pair is a superseded unpair (re-pair reuses the pairId; AD-07's epoch distinguishes sessions) and is dropped; an *un*shredded row with a live pair is a crash mid-initiate and its shred is still owed. (6) **7-day timeout → `LOCAL_ONLY_TERMINATED`, never TERMINAL** (`UnpairState.CONFIRM_TIMEOUT_MILLIS`; `phaseAt` derives the phase from `confirmedAt`/timeout/role, no stored phase column to drift). A late ack strictly upgrades: newer evidence is better evidence, and it is still the partner's own device confirming. (7) **Revocation ordering:** `/pairings/{pairId}` flips to `terminated` once the request is out (delivered *or* timed out — an undelivered unpair must not leave the credential writable forever); the rules allow exactly that transition. The loser of a mutual unpair simply loses the race: a denied terminate is a no-op, not a failure. (8) **Rules amendments (deploy pending).** Pairings: member-only update, `status` the only affected key, `active → terminated` one-way; create/delete still denied. Acks: readable by the recipient **or the message's author** (`exists(msg) && get(msg).data.senderUid == auth.uid`) — without this the initiator can never confirm. Six new rules-emulator cases pin both: member terminate allowed, re-open denied, field-smuggling denied, non-member denied, re-terminate denied; author reads own message's acks, non-author denied. (9) **UI copy is the plan's three strings verbatim, plus honest dialog/responder copy** (`strings.xml`): "This erases your partner's data on this device immediately. Your partner's phone erases its own copy next time it's online — that part can't be forced." on the confirm dialog; "Your data on this device has been erased" the moment local shred completes; "Waiting to confirm your partner's device has also erased its data" until confirmation; "Could not confirm your partner's device erased its data." after the timeout; the responder sees "Your partner ended the partnership. Your data for it on this device has been erased." plus an "…letting your partner's device know…" state while an owed ack is retried. `PartnerScreen` renders `UnpairCard` (biometric-gated initiation via `MainActivity` — cancelled/refused leaves the pair untouched) and the role-aware `EndedCard`; Dismiss is guarded by `isDismissible` (never dismissible while the wait is still honest; a responder can't dismiss with an owed ack — that would strand the initiator's confirmation). The dashboard reads live enrollment state on every load, so the tab flips to `Unpaired` with no clearing logic (ADR #47 Consequences).

**Verification:** JVM (Robolectric, real Room + real crypto; Keystore/mailbox/ack endpoints are constructor-seam fakes) — new `BilateralDeletionTest`, 11 cases: partner-reachable confirms on ack → TERMINAL with delivery+shred bookkeeping asserted at the pre-confirmation instant; partner-unreachable through the accelerated 7-day window → `LOCAL_ONLY_TERMINATED` with no confirmation timestamp, asserted *distinct* from TERMINAL; late ack after timeout upgrades to TERMINAL; crash before event creation → resume still shreds from the row alone and doesn't terminate early; re-paired pair drops the shredded superseded row but keeps an unshredded one's shred owed; failed creation leaves no row and no shred; re-entering initiate continues the same attempt (same message id/timestamp, no second drain or event); initiate drains every pending batch before shredding; undelivered request journals the bytes for a post-wipe redelivery; responder shreds → acks → TERMINAL → dismisses; owe-ack blocks dismissal until it goes out. `AccountabilityDatabaseMigrationTest` +1 (`migration7to8_addsUnpairJournal_preservingV7Enrollment`: v7 DB, enrollment `pairing_epoch=2` intact, unpair row round-trips, `phaseAt` AWAITING → TERMINAL after `markConfirmed`), with the v7 DDL companion. `MailboxMessageHandlerTest` rewritten for the v2 path: a deletion request is shredded, never chained, never generically acked/notified (the ack rides the shred), and a failed shred reports `DELETION_FAILED` unacked and re-deliverable. Rules emulator: suite 18/18, including the 6 new termination/ack cases. Full JVM suite 618/0/0. androidTest + main compile. **§12 line 526's mandated scenario (reachable → TERMINAL vs unreachable → LOCAL_ONLY_TERMINATED, reported distinctly and accurately) is covered by the three initiator tests; the mandated *UI* reporting rides `phaseAt`-derived copy pinned in `PartnerScreen`/strings.** Device leg: none exists for this step as specified — the two-device evidence route is the ADR #46 virtual-partner harness (an emulator cannot attest), tracked with the other queued device legs; the protocol logic is entirely JVM-covered.

**Trade-off Accepted:** (a) **Mutual-unpair race:** the first `terminated` write wins; the other side's terminate is denied and ignored — both devices still shred locally, so the security outcome is identical either way. (b) **Ack-retention bound:** AD-18b mailbox cleanup can delete the request message (and its ack) before an offline initiator ever polls — the result is the honest under-claim (`LOCAL_ONLY_TERMINATED`), never a false TERMINAL; accepted, because the alternative (trusting delivery bookkeeping) would over-claim, which AD-13b/§17 forbid. (c) **Key destruction is device-level** (one agreement key serves all pairs — §10): shredding one pair renders every pair's stored ciphertext unrecoverable. Deliberate; the single-pair user pays nothing, a multi-pair user losing one pair loses the others' history — inherent to the §10 design, recorded here because it's the sharpest edge in the protocol. (d) **The responder never persists the partner's uid** — the ack path needs only the message id + its own mailbox; one less identifier retained. (e) **`terminatePair` failure is logged, not retried to completion** — the next pass retries it (it's inside `resumeRequester`/`resumeResponder`'s flow), but a permanently-denied terminate degrades to a writable-but-dead pairing row, not to local data exposure (the keys are already gone).

**Consequences:** **Deploy gate:** `firebase deploy --only firestore:rules` must run with the user's approval — until then the terminate + ack-read amendments exist only in the repo and emulator, and production unpair still cannot complete (Req 29 remains silently broken until deploy). Step 15 (rotation) is untouched by unpair. Step 16's notification story gains the unpair event copy (generic partner-event channel). Step 19's R-08 metric ("unpair stuck in UNPAIR_REQUESTED / timed out") maps to `phaseAt` on the journal rows — no new storage needed. The ADR #46 harness is the template for the one queued device leg (unpair end-to-end on two attesting identities).

**ADR \#50 Title: Session Key Rotation (Step 15) — CEK-Layered Per-Epoch Derivation, Absent-at-Zero `ke` Wire Field, and the Receive Policy as the Honest "Discard"**

**Status:** Accepted; implemented 2026-09-19 (client; JVM-verified). Authoritative spec: plan v2 §7 item 15 (line 262), §8 Step 14 (lines 431–433), AD-12 (line 192), AD-08 (line 176), §8 Step 9 receive pseudocode (lines 393–406), §12 line 514, §17 lines 634–635, §10.

**Context:** AD-12 bounds the exposure of each derived session key by rotating it every 500 events or 30 days, and mandates that "every event envelope carries an explicit `keyEpoch` field so the receiver selects the correct key deterministically rather than trial-decrypting." §8 Step 14 adds that the "prior epoch's key is retained for 7 days (to support in-flight repair replays referencing it), then zeroed." Three implementation realities shaped the design. (1) **Nothing can actually be zeroed.** Session keys are HKDF outputs derived on demand from the pair's CEK, and the CEK lives for the life of the pairing — there is no session-key storage to destroy and no moment at which re-derivation becomes impossible. The honest, enforceable reading of "zeroed" is therefore a *receive policy*: after the grace window the device refuses to derive that epoch's key at all, so old ciphertext becomes unusable in practice even though the math still exists. The ADR states this plainly rather than claiming a cryptographic erasure the protocol cannot perform. (2) **Every stored envelope must stay byte-valid.** Envelopes are signed-and-hashed material persisted in the chain table and (for undelivered traffic) in the outbox as pre-built bytes; re-encoding epochs into existing envelopes would invalidate signatures and break §12's byte-identical retransmit guarantee. A new wire field must therefore be *absent* — not zero-encoded — at epoch 0, so every pre-rotation envelope keeps its exact bytes. (3) **The 30-day threshold needs an anchor both devices agree on.** The two devices never reconcile clocks; any locally-fabricated start time would claim an observed age the device never measured. The plan's own pseudocode routes a key-epoch mismatch to `UNKNOWN_KEY_EPOCH` — a state AD-08 explicitly places *outside* `TAMPER_SUSPECTED` — and the DB whose schema evolves here is the accountability chain DB (§17's "SQLCipher migration v8→v9" is this DB; the rules store is untouched by this step).

**Decision:** (1) **Per-epoch derivation layered on the CEK** (`CekDerivation.deriveSessionKey`): epoch 0 **is** the raw CEK (pre-rotation ciphertext and the animated-QR pairing budget stay valid), epoch *n* is `HKDF(CEK, "StrictMode-session-key" || BE32(n))`. Both sides derive identically from the shared CEK alone — no key exchange, no new state to disagree about. (2) **Wire field `ke` (CBOR key `keyEpoch`), absent at 0** — an epoch-0 envelope encodes byte-identically to its pre-Step-15 form and its signature still verifies; above 0 the field is signed material (`EnvelopeTest.keyEpoch_zero_leavesTheWireFormatUntouched` pins the absence, `keyEpoch_roundTripsAboveZero` the round trip). (3) **`SessionKeyManager.rotateIfDue(pairId, senderKeyId, now)`** rotates when `lastSequence − keyEpochStartSequence >= 500` **or** `now − keyEpochStartedAt >= 30 days`; the new epoch is written to `ChainState` (`advanceKeyEpoch`) and stamped onto every subsequently created envelope, so rotation happens on the send path *before* the envelope is built (`EventCreator`), and the sync coordinator exposes it as a reportable step (`SyncReport.rotatedKeyEpoch`). (4) **Anchor honesty.** `key_epoch_started_at` is the epoch's first event's signed `createdAtEpochMillis` — the same value on both devices, no clock reconciliation — and `key_epoch_start_sequence` is the last sequence before the boundary. A head from an older schema has **no anchor** (NULL), and the manager refuses to rotate until an event stamps one: a fabricated backfill would claim an age never observed. `acceptsIncoming` similarly treats an unanchored head as not-yet-expired. (5) **The 7-day grace is a receive policy, and `UNKNOWN_KEY_EPOCH` is its own outcome.** `acceptsIncoming` accepts the current epoch, any *forward* epoch (a receiver catching up across missed rotations derives the declared one), and the *prior* epoch only within 7 days of the anchor; anything older is refused. On the receive path (`MailboxEventProcessor`) the refusal is checked **after** signature verification and **before** decryption, yielding `EnvelopeResult.UnknownKeyEpoch` → logged as the AD-08 security event — never notified, never acked (so a legitimate repair replay can be redelivered), never chained, and **never** `TAMPER_SUSPECTED` (AD-08 line 176). Each message resolves its own epoch key from a per-message head snapshot (`FirestoreMailboxReceiver`), deterministically — `MailboxEventProcessorTest` asserts exactly one epoch is probed, never trial decryption across epochs. (6) **DB v8→v9** (`MIGRATION_8_9`): two added `chain_heads` columns with NULL/0 defaults, so a pre-existing head keeps its epoch and simply waits for its next event to anchor. (7) **Latent bug fixed in the same change:** the live `provideAccountabilityDatabase` DI builder was missing `MIGRATION_7_8` (only `AccountabilityDatabase.get` and the tests registered it), so any installed v7 device upgrading to the current build would have crashed opening the DB — the builder now registers 7_8 **and** 8_9. (8) **Deviation, recorded:** the mailbox outbox's own `key_epoch` field is the *identity*-epoch relay metadata (AD-07) and stays unchanged; the signed envelope's `ke` is the authoritative session-key epoch on the wire.

**Verification:** JVM (Robolectric, real Room + real crypto) — new `SessionKeyManagerTest` (8 cases: rotation at exactly 500 events with the new anchor asserted; just-below-both-thresholds no-rotation; rotation at 30 days with zero traffic; an unanchored head waits for its first stamped event; second rotation counts from the previous boundary, not from epoch 0; append anchors a deferred epoch from the envelope's signed creation time; a received later epoch advances + anchors the head and same-epoch traffic keeps it; `acceptsIncoming` across null-head/current/forward/prior-inside-grace/prior-expired/older-than-prior/unanchored). `EventCreatorTest.rotationDue_newEnvelopeCarriesTheNextEpochUnderItsSessionKey`: a head at 500 events → created sequence 501, envelope declares `keyEpoch` 1, head advances, and the partner re-derives the same session key **from the CEK alone** and decrypts. `MailboxEventProcessorTest` +2: refused epoch → its own `UnknownKeyEpoch` result (never Corrupt, never InvalidSignature) and the declared-epoch-only probe assertion. `EnvelopeTest` +2 (absence at 0 / round trip above 0). `AccountabilityDatabaseMigrationTest` +1 (`migration8to9_addsRotationAnchors_preservingTheHead`: v8 DB with a head at `key_epoch=2` → epoch preserved, `key_epoch_started_at` NULL, `key_epoch_start_sequence` 0), all five earlier cases extended through `MIGRATION_8_9`; `EnrollmentDaoTest` also registers it. Full unit suite 632/0/0/0 across 85 classes (was 618; +14). **§12 line 514 ("both thresholds; verify old-key retention/discard timing") is covered by the `SessionKeyManagerTest` pair of threshold cases plus the grace-window cases in `acceptsIncoming`; §17 line 635 (same criterion) rides the same tests.** §17 line 634's instrumented `MigrationTestHelper` variant (full encrypted driver stack, interrupted-migration scenario) stays with Step 20's full-suite task — it needs the complete SQLCipher `SupportFactory` instrumentation stack, not a JVM leg.

**Trade-off Accepted:** (a) **"Prior key zeroed" is a policy, not a destruction** — the derivation math from the CEK remains possible forever; what the grace window buys is that the *device* refuses, which is the only honest claim deterministic derivation supports (Decision 1/5; ADR language matters here per AD-12's own "not forward secrecy" wording). (b) **The repair-replay window and the rotation grace are the plan's numbers, not a merged design** — a repair replay referencing an epoch more than one rotation back, or past the 7-day grace, cannot be decrypted; the chain then reaches `CHAIN_INCOMPLETE` (AD-08's genuinely-gone state). The 30-day repair window vs the 7-day key grace is an inherent tension in AD-12/§8 as written; the implementation follows the plan's numbers and this ADR records the seam rather than silently widening either. (c) **Clock skew affects only the grace comparison** — anchors are signed creation times, so skew shifts the grace boundary by the skew, never the epoch identity. (d) **`ke` is absent-at-0 rather than explicitly 0** — chosen for byte compatibility at the cost of one optional-key branch in the decoder; the alternative (always-present field) would have invalidated every stored signature.

**Consequences:** Step 16's notifications and Step 19's metrics are untouched by rotation (any `UNKNOWN_KEY_EPOCH` count rides the security log). The wire format is now versioned by construction: any future rotation-scheme change rides a new `ke` value, and the AD-08 `PROTOCOL_MISMATCH` slot remains reserved for a genuine protocol-version field. A device that receives an epoch it refuses will re-receive it after the sender's repair responds again — the refusal is deliberately not acked so nothing is lost silently. The one deploy-adjacent note: none — this step is client-only; the pending rules deployment (ADR #49) is unrelated.

**ADR \#51 Title: Notification Permission Flow + Channels (Step 16) — Banner-as-Rationale, Session-Scoped Requestability, and Creation-Time Channel Enumeration**

**Status:** Accepted; implemented 2026-09-19 (client; JVM- and device-verified). Authoritative spec: plan v2 §7 item 16 (line 263), §8 Step 16 (lines 434–436), §10 error table (line 462), §12 line 523, §14 line 579, §17 line 631.

**Context:** §8 Step 16 specifies a flow — `areNotificationsEnabled()` → rationale → request `POST_NOTIFICATIONS` (13+) → if denied, persistent dashboard banner with a settings deep link → re-check on every foreground — plus three channels (`partner_alerts` HIGH, `approval_requests` HIGH, `sync_status` LOW, "used only for internal/debug visibility, not shown to the user in production builds"). Three realities shaped the implementation. (1) **The platform's rationale API cannot carry the flow's first two arrows.** `shouldShowRequestPermissionRationale` returns false both before the first ask and after "Don't ask again"; those two states need different UI (raise the dialog vs. deep-link to settings), so the step needs state the API does not provide. (2) **Channel importance is immutable after creation** — a platform policy (a channel's importance belongs to the user once the channel exists; `createNotificationChannel` with a different importance is a no-op). The spec is therefore enforceable at first creation only, and the Step-16 audit found `partner_alerts` was in fact being created at DEFAULT importance by the pre-existing helper — a spec violation invisible on devices that already carry the old channel but real on every fresh install. (3) **"Notifications are off" has two causes** — the runtime permission and the app-level toggle — and the banner must key off the effective post gate, `NotificationAccess.canPost` (the single gate every notification surface already routes through), or it would lie in one direction or the other: hiding while posts silently drop, or showing while posts succeed.

**Decision:** (1) **Banner-as-rationale.** The Partner-screen banner's body copy is the rationale ("MyExodus can't tell you when new partner activity arrives"); its single action button realizes the remaining arrows: "Allow notifications" while the dialog can still be raised, else "Open notification settings" (`Settings.ACTION_APP_NOTIFICATION_SETTINGS` + package extra, via the existing `notificationSettingsIntent`). No separate pre-dialog rationale screen — it would add a tap with zero information over the banner copy. (2) **Session-scoped requestability** replaces the rationale API: `canRequestNotifications = SDK_INT >= 33 && !notificationsRequested && permission != GRANTED`, with `notificationsRequested` a `rememberSaveable` flag set on the ActivityResult callback. Worst case (the flag is reset by process death) the button re-offers the dialog and a "Don't ask again" user's system silently denies — the settings link is the always-correct fallback, so no state can strand the user. (3) **Re-check on every foreground** (the spec's last arrow): `notificationsEnabled` is initialized from `canPost` and re-read in a `LifecycleEventObserver` on `ON_RESUME` (`MainActivity`). (4) **Channels finalized at creation time** (`PartnerNotifications`): `partner_alerts` HIGH (**audit fix** — was DEFAULT), `approval_requests` HIGH (own channel so requests/decisions can be silenced separately from activity alerts), `sync_status` LOW. Partner/approval channels are created lazily at first post (idempotent, the existing pattern); `sync_status` is created once in `MyExodusApp.onCreate` behind `BuildConfig.DEBUG` — a release build never creates the channel at all, satisfying "not shown to the user in production builds" by construction, and no production code posts to it either. (5) **Denied = silent no-op, via the existing gate.** `NotificationAccess.canPost` returns before any post on every surface; §12 line 523's "no crash when a notification is attempted while denied" is exactly that return path, and it holds everywhere because every notification surface shares the one gate.

**Verification:** JVM (`PartnerNotificationsTest`, 4 cases): denied → post is a silent no-op, no channel created, no active notification; granted → `partner_alerts` exists at `IMPORTANCE_HIGH` with exactly one notification posted; `approval_requests` at HIGH with request + decision posted; `sync_status` at LOW with nothing posted. Full unit suite 636/0/0/0 across 86 classes (was 632/85; +4 tests, +1 class — `PartnerNotificationsTest`). **Device (X6532, debug build), photographed end-to-end:** banner visible in the denied state with "Allow notifications"; tap raises the system permission dialog; "Don't allow" flips the button to "Open notification settings" (the persistent denied state); `dumpsys notification` shows `sync_status` at mImportance=2 (LOW), the debug-only channel present; after re-granting, a relaunch that delivered a real `ON_RESUME` (task-to-front after backgrounding — a plain `am start` on the foreground activity is `onNewIntent` and correctly does not re-check) cleared the banner, the foreground re-check observed working. Two honest readings from the same dump: `partner_alerts` reads mImportance=3 **on this device only** because the channel pre-existed at DEFAULT from an earlier build (immutability — Trade-off (a)); `approval_requests` had not yet been posted to this device (no approval event has fired there), so its creation-time shape is pinned by the JVM case rather than the dump. §17 line 631 (denied state detected and surfaced via the banner) is the device leg above; §12 line 523 rides the JVM denial cases.

**Trade-off Accepted:** (a) **Pre-existing channels keep their old importance** — devices that already carry `partner_alerts` from a pre-Step-16 build will not be raised to HIGH; the platform forbids it (importance is user-owned after creation, and deleting/recreating the channel to dodge the rule is not available to apps and would be user-hostile anyway). Fresh installs get the spec'd values; the JVM case pins the code that will run there. (b) **The session flag can be wrong only by re-asking** — process death resets it, costing at most one already-denied dialog tap; the settings path is always correct, so the worst failure mode is a redundant tap. (c) **The banner lives on the Partner screen**, not in global chrome — it is the surface whose events depend on notification delivery (§10 line 462's "persistent dashboard banner"), and placing it where the consequence is visible beats a global strip the user learns to ignore. (d) **`sync_status` existence is gated by build type, not a runtime flag** — the cleanest reading of "not shown to the user in production builds": a release binary contains no code path that can create it.

**Consequences:** Step 19's §14 metric "notification-permission-denied rate among active pairs" (line 579) reads the same `canPost` state the banner reads — no new plumbing. ADR #49's unpair copy rides the now-HIGH `partner_alerts` channel. No deploy gate — client-only. Invariant for future work: a channel's importance is established at creation and never after, so any future change to a channel's spec requires a **new channel id**, never an edit to an existing one.

**ADR \#52 Title: Local-Data-Wipe Detection (Step 17) — the Agreement Key as the Out-of-DB Prior-Pairing Signal, Idempotent Re-Derivation, and the Card Instead of a Recovery Flow**

**Status:** Accepted; implemented 2026-09-19 (client; JVM- and device-verified). Authoritative spec: plan v2 §7 item 17 (line 264), §8 Step 17 (lines 438–439), AD-22 (line 222), NFR7 (line 61), §9 error table (line 465), §12 line 522, §14 line 580, §17 line 637.

**Context:** AD-22/NFR7: a local-data wipe — the expected database missing or undecryptable, on a device that otherwise shows signs of prior pairing — is detected **at app start**, forces re-enrollment via SAS/QR, and explicitly never attempts to silently recover the session; the server-side pairing record is left to expire rather than actively torn down. Three v2 realities shaped the implementation. (1) **The plan's "SQLCipher DB" is the accountability chain database, which v2 runs as plain-FBE Room** (SQLCipher is the rules store — a different store, untouched by pairing). The *mechanism* the plan cares about — "fails to open/decrypt with the Keystore key that should exist" — collapses in v2 to the file simply being gone or unreadable; what survives unchanged is the required **signal and behavior**, not the storage encryption. (2) **The prior-pairing signal must live outside the database**, which is why the plan names a Keystore-alias check. v2's agreement key qualifies structurally: it is destroyed **before** its enrollment on every legitimate shred path (`BilateralDeletion.shredIfPending` / `handleIncoming`, ADR #49), so *key present + enrollment absent* cannot be a normal unpair — it is the definition of the wipe. (3) **No production pairing UI exists** (harness-only; Open Product Decision #16), so "route to the SAS/QR re-enrollment flow" cannot be a button that launches a flow; the honest v2 realization is a distinct Partner-screen state that names re-enrollment as the only route forward.

**Decision:** (1) **Detection = key present, enrollment absent** (`LocalWipeDetector`, function seams, JVM-tested): `hasAgreementKey()` true **and** the enrollment read returns nothing → wipe. An **unenumerable** read (the database cannot be opened at all — the plan's "fails to open/decrypt" branch) is reported as a wipe **without** attempting the clear, since nothing can be read to clear; either way detection is re-derived at every start and never persisted as a flag. (2) **The wipe clear is global and pair-scoped.** `ChainStateStore.wipeAllPairData()` deletes exactly the tables an enrollment would have owned — outbox, chain events, chain heads, approval requests — in one write transaction. Deliberately surviving: the unpair journal (ADR #49's must-outlive-the-pair rule; a pending unpair legitimately resumes and completes, destroying the key and finishing as a normal `Ended`), `processed_events` (messageId-keyed replay protection, pair-less), and enrollments themselves (none by detection's premise). (3) **No recovery, structurally.** Nothing re-derives the CEK or rebuilds chain state; the mailbox and repair paths are enrollment-gated everywhere (drainer, sync coordinator, receiver), so with no enrollment nothing drains, pulls, or repairs. (4) **App-start hook** in `MyExodusApp.onCreate`'s post-unlock block: one suspend call, best-effort (`runCatching` inside the detector — the clear re-detects next start; detection can never crash startup), and one telemetry event `nonFatal("local_wipe_detected")` — the §14 line 580 trigger count. (5) **UI: a `PartnerDashboardUi.WipeDetected` state** (its own `InfoCard`, no CTA). **ADR \#53 Title: Server-Side Rate Limiting (Step 18) — Counter Extraction for Call-Count Proof, and the Author-Read Rail That Makes a Rejection Observable to Its Sender**

**Status:** Accepted; implemented 2026-09-19 (server + client + rules; JVM/function/rules-emulator-verified; rules deployed 2026-09-19 — user approved the amendment, task #33 closed). Authoritative spec: plan v2 §7 item 18 (line 265), §8 Step 18 (lines 441–442), AD-23 (line 224), §9 error table (line 461), §11 line 503, §12 line 541, §17 line 638.

**Context:** AD-23 fixes the thresholds — 10 events/pair/min, 200 mailbox messages/sender/day, enforced in the Cloud Function *before any push dispatch work* — as fixed-window counters in `/rate-limits/{pairId}` (the 5-SOS/hour clause was dropped by user ruling, ADR #42: the relay sees ciphertext and cannot classify an event as SOS; not re-litigated here). §12/§17 line 638 require the ordering to be *provable*: "Rate limit rejection occurs before any installation lookup or dispatch attempt (verified via call-count assertions on the dispatch mock)." §8 line 442 / §9 row 461 add the client half: "Rejected writes surface to the sending client as a `RATE_LIMITED` mailbox-write failure, distinct from a network failure, so the UI can message it accurately rather than showing a generic 'couldn't send' error." The client half is structurally awkward in v2: the sender's mailbox **write succeeds** (rules allow create), and the *relay* — triggered on document creation — merges `{relayStatus, relayedAt}` onto the document the recipient owns. So the rejection marker exists, but on a document the sender could not read.

**Decision:** (1) **Server: pure logic extracted for provability.** `incrementWindows(data, senderUid, now)` (pair + per-sender fixed windows, rejection checked before any counting) and `createRelayHandler(deps)` (every effect injected: `pairingActive`, `checkRateLimit`, `markMailbox`, `listInstallations`, `dispatch`, `logger`) live in `relay-logic.js` with no admin-SDK dependency; `relay.js` is SDK wiring only. Handler order is validate → pairing → **rate limit (marks the mailbox `RATE_LIMITED`, returns)** → installation lookup → dispatch; the node suite asserts the call *counts*: on rejection, `listInstallations` 0 and `dispatch` 0 — §12's requirement verbatim, in a comment on the test. Rejection is cheap *and* early (§11 line 503). (2) **Rules amendment (deploy pending): the message's author can read its own message document** — `allow read: if request.auth.uid == recipientUid || resource.data.senderUid == request.auth.uid`, the same author-read shape as the Step-14 ack rule (ADR #49). The author already wrote every field here (content, ciphertext, pairId); only "was it relayed" is newly visible. (3) **Client read-back:** DB v9→v10 adds two nullable `outbox` columns — `relay_checked_at` / `relay_rejection` — because §6 step 8 defines SENT as *mailbox write succeeded*, which stays true; the rejection is separate state, not a status change. `MailboxRejectionChecker` reads the relay marker for due rows and stamps the outcome. **Due** = `relay_checked_at IS NULL OR relay_checked_at > now − 1 h` — the relay is asynchronous and a partner push wake can start a sync pass seconds after a drain, so a single no-marker look would false-negative; re-checks make it self-healing. A **read failure leaves the row due** (never stamped) — exactly as a network failure leaves the drainer's row PENDING; a failed due-query is 0, never an exception into the sync pass. (4) **Ordering client-side: the rejection check runs before the drain**, so this pass's own writes are not yet SENT and can never be checked against a relay that has not run. `SyncReport.rejectionsFound` reports the finding. (5) **UI copy names the real consequence:** `PartnerDashboardSource.Paired.rateLimitedRecently` (a rejection stamped in the last 24 h) drives one line in the SyncCard — "Some recent updates came in faster than the server allows, so they weren't sent as instant alerts. They'll arrive with the next sync." — deliberately not the "couldn't reach the server" copy (`partner_check_now_failed`): the network is fine and the update is not lost. Pulled events still notify (`MailboxMessageHandler` notifies on receipt), so a rate-limited message arrives and alerts at the next sync — the copy says precisely that.

**Verification:** Server (`npm test`, 30/30; +7): `incrementWindows` — 10 allowed then the 11th rejected without being counted, per-sender independence, day-span reset; handler via a call-recording harness — rejection → `markMailbox [['m1','RATE_LIMITED']]`, `listInstallations` 0, `dispatch` 0 (§12 verbatim); oversized payload rejected before even the pairing check; inactive pairing before the rate limit; accepted message dispatches to every installation; zero installations → nothing recorded, nothing dispatched. Rules emulator (`npm test`, 19/19; +1): alice writes m1, a rules-disabled update sets `relayStatus: 'RATE_LIMITED'`, alice's get succeeds, a non-author's fails. JVM (**655/0/0/0 across 88 classes**; +7 over Step 17's 648/87): new `MailboxRejectionCheckerTest` (4 — marker recorded; read failure stamps nothing so the row stays due; due-query failure never fails the sync pass; the due window is `now − 1 h` pinned via the argument); `PartnerSyncCoordinatorTest +1` (the check runs before the drain — step order asserted — and its count rides the report, drain undisturbed); `PartnerDashboardSourceTest +1` (recent rejection → `rateLimitedRecently`; clean → false; a failed read is "not evidence of a rejection"); `AccountabilityDatabaseMigrationTest +1` (v9→v10 preserves the event + SENT outbox row byte-intact, `relayCheckDue` finds it, `stampRelayCheck` removes it from due and `rejectionCountSince` sees it) with the V9 DDL companion, all five migration lists + `EnrollmentDaoTest` extended; `node --check` on both function files. §17 line 638 rides the call-count tests; §9 row 461 rides the distinct state + copy.

**Trade-off Accepted:** (a) **A rate-limited message is still delivered — later.** The sender's write landed, so the recipient's next pull receives and notifies it; the rejection means "not relayed as an instant alert", and the UI copy says exactly that rather than implying loss. (b) **A rejection is observable only after the relay ran and a later sync pass re-read the row** — up to the 1 h settle plus the next sync; the honest alternative (immediate failure feedback) would require the send path to block on a server round-trip that §6's SENT definition deliberately does not include. (c) **The author-read amendment widens mailbox reads** to the document's own author — the same actor who wrote it; no third party (the pairings probing guard and recipient-only writes are untouched). (d) **The 5-SOS/hour clause is absent by ruling, not by omission** (ADR #42).

**Consequences:** **Deploy gate (closed 2026-09-19):** the three amendments (Step-14 termination, ack author-read, this mailbox author-read) went out via `firebase deploy --only firestore:rules` after explicit user approval — gate re-run 19/19 immediately before, deploy compiled + released cleanly (project `myexodus-53804`). Step 19's R-02 metric ("Rate-limit rejection metrics on the HMS/no-GMS path") reads the outbox rejection counter — no new storage. Function thresholds are the authoritative abuse control (§11 line 483); the client-side SOS cooldown remains UX-only. Invariant for future work: any new relay-side rejection reason must be recorded on the sender's document (`markMailbox`) so the author-read rail surfaces it, and any new relay step that costs money belongs **after** `checkRateLimit` in `createRelayHandler`.

**ADR \#56 Title: Push-Registration Rollout Gate (Plan v2 §13 line 564) — Remote Config, Kill-Switch Semantics, Default On**

**Status:** Accepted; implemented 2026-09-19 (client; JVM-verified). Task #28. Authoritative spec: plan v2 §13 line 564 ("Staged client rollout: `push_installations` registration is gated behind a feature flag, independent of app-store release cadence").

**Context:** The plan requires the registration rail to be togglable without shipping an APK. Two implementation realities shaped the choice. (2) **The default direction is a real product decision, not a detail.** There is no production install base to stage across (no pairing UI has shipped), and default-OFF would silently stop a working registration rail on every existing device and harness flow the moment the flag ships; default-ON with a remote disable keeps today's behavior until a rollout is deliberately halted. (3) **DI wiring** (AccountabilityModule): `FirebaseRemoteConfig.getInstance()`, minimum fetch interval 900 s (one fetch per sync cadence; a console flip lands within one pass), `setDefaultsAsync(mapOf(PUSH_REGISTRATION_CONFIG_KEY to true))` before the first read. Key: `partner_push_registration_enabled`. (4) **Halting means skipped registration, not deregistration** — an existing `push_installations` row stays until its staleness window (Step 6 sweep treats stale rows as terminal); the flag stops new/updated registrations, it does not reach into partner devices.

**ADR \#58 Title: Approval-Flow Device Leg (Task #32 — Extending the ADR #46 Harness, and the DI Migration-List Gap the Leg Caught: 9→10)**

**ADR \#60 Title: Leaf Logo Brand Identity (2026-09-19) — Keyed-Alpha Icon Pipeline, White-Field Adaptive Icon, and a Brand Plate for Night Mode**

**Status:** Accepted; implemented 2026-09-19. Authority: user-supplied brand masters (`design/brand/myexodus-logo-master.jpeg` 1024² white-field, `myexodus-logo-on-black.jpeg` 500²); user decision 2026-09-19 (white icon field, "use them anywhere that applies — be critical"). Supersedes the Desert Dawn vector mark (`ic_launcher_foreground.xml`'s sun/horizon) as the app's identity.

**Context:** The app shipped with a vector "Desert Dawn" sun mark as its launcher icon. The user supplied the real logo — a three-leaf gradient mark plus a `MyExodus` wordmark — as JPEGs, i.e. with no alpha channel: "no background" was a black field, not transparency. Every icon surface (adaptive icon, legacy rasters, Android 12+ splash, notification silhouette) and both in-app identity surfaces needed the new mark.

**Decision:** (1) **Alpha is derived, not assumed** — `design/brand/GenerateIcons.java` keys the white field out of the master on a Chebyshev distance-to-white ramp (30 → transparent, 80 → opaque) and un-premultiplies the surviving colour off white so antialiased edges carry no pale halo. A *global* threshold, not a border flood-fill: the design has white **inside** it (the separation gap where the stem crosses the leaves is background, and it must key out too). (2) **The mark is split from the wordmark by measurement, not by eye** — the row-ink profile's widest empty band in the middle 40–92% of the ink extent is the gap; the script throws rather than emit a mis-split asset. (3) **White field, per the user's pick** — the adaptive icon is `@android:color/white` with the mark as a per-density 108dp PNG foreground, sized so the bbox diagonal ≤ 60% of the canvas, i.e. inside the 66/108dp safe circle: no OEM mask crops the leaf tips (the app targets every skin, so the *guaranteed* zone is the only safe budget). Legacy rasters (48–192px) are the mark on a white square / white circle. (4) **In-app art sits on a white plate** — the wordmark and stem are dark green, which the near-black `SandDark` surface swallows entirely; `ui/BrandMark.kt` therefore draws both the lockup and the mark on a white chip (invisible in light mode where the surface is already white, an app-icon-style chip at night). The plate is brand, not palette, and stays white in both modes. (5) **Placement, deliberately sparse** — launcher icon + splash (automatic), the lockup on the wizard's **first** step only (a repeat on all five permission steps would be chrome), and the mark beside the Settings title (the app's only about-ish surface). Notification small icons need no change: `minSdk = 26` means the system derives the silhouette from the adaptive foreground's alpha, so they now read as a leaf. (6) **The retired mark is deleted, not kept** — the two vectors and the ten legacy `webp` rasters are gone; git is the archive.

**Verification:** `:app:assembleDebug` BUILD SUCCESSFUL. X6532: app-info page renders the white-field leaf (adaptive icon live); Settings header renders the mark chip in **dark mode** (the case the plate exists for); the app-installed launcher entry resolves to the new mipmaps. Emulator (API 36): Android 12+ splash renders the leaf on the sand window background. `logo_mark.png` composited over `SurfaceDark` by an independent checker — 53.1% fully transparent / 45.0% fully opaque, no white box. Honest gap: the wizard's lockup was **not** observed on screen — the physical device has already completed first-run (its flag was left untouched) and the emulator could not complete a cold start under host CPU contention (the same condition ADR #59 recorded); the component itself is the one verified in Settings, composed the same way.

**Trade-off Accepted:** (a) **The in-app lockup shifts the wizard layout on step 0→1** when it disappears; a permanent header would be stabler but repetitive on a permission screen. (b) **The adaptive mark is conservative (~63% of the visible area)** — a tighter fit would look fuller at large sizes but risks shaving the pointy leaf tips under a circular mask on some OEM skins. (c) **Assets are regenerated by running a JDK single-file program from the repo root**, not by a Gradle task — a build-plugin would be machinery for a step that changes when the brand does. (d) **`drawable-nodpi` bitmaps, capped at 256/320px**, rather than density buckets: they are scaled by Compose, and the cap keeps the decoded bitmaps off the heap's large-object path.

**Consequences:** The brand has one source of truth (`design/brand/` masters + the generator) and every surface derives from it, so a future brand tweak is one run, not eleven hand-edited files. The ADR #59 "known limitation" about API 24/25 rasters still showing the template robot is retired by this change. Icon geometry decisions (safe-circle diagonal, plate rationale) are recorded here rather than inferred from PNGs.
