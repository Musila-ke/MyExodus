Revisions made during implementation (each with its reason)

  • §8.7 gap threshold — the plan's "cadence plus tolerance margin (initial default: cadence × 3)" is implemented literally, with the cadence pinned by Step 1 to the 30 s heartbeat (not the 1.5 s enforcement poll): 30 s + 3 × 30 s = MEASUREMENT_GAP_THRESHOLD_MS = 120 s. The formula reads the heartbeat cadence, so the threshold follows the constant if the cadence ever changes. Shipped in AccountingDiagnostics.
  • §8.7 escalation threshold fixed at 5 minutes (the plan named the requirement without a value). Below 5 min a restart is ordinary churn and a prompt would be noise; revisable on device evidence. Shipped as AccountingDiagnostics.ESCALATION_THRESHOLD_MS.
  • AD-16 deviation, deliberate: reboot-spanning intervals are reconstructed via UsageStatsManager when permission is held (recorded as RECONCILIATION), rather than always recorded as uncredited measurement_gap tagged reboot_boundary. Rationale: the plan's own §8.9 reconciliation machinery already existed, the reboot case is the single largest real-world credit loss, and the conservative credit-only-going-forward rule of R12/AD-18 is preserved — the reconciliation never backdates a total the user already saw. When permission is absent, the plan's uncredited-gap behavior is exactly what ships. Documented in ADR #94.
  • Zero-length reboot convention: the first observation after a boot-count change records the boundary as a zero-length interval so elapsed time is never subtracted across boots (R5) while still giving every boot a ledger anchor.
  • Day-boundary clip (§8.5/§8.11): an interval crossing local midnight is split proportionally; a span ≤ 0 or a boundary outside the span degrades to the closing-day single slice. Midnight is computed in elapsed space against the boot-relative anchor.

1. Feature Overview

This feature replaces the mutable daily usage scalar in AppRulesStore with an append-only usage ledger (Room schema v10 → v11, SQLCipher-encrypted). The ledger is the single source of historical truth for usage accounting and diagnostics. A transactionally-coupled current-day projection provides fast enforcement/UI reads without re-aggregating the full ledger on every check.

User-visible behavior:

  • Existing app rules, limits, and all v10 data survive the migration.
  • The user's in-progress daily usage total at the moment of upgrade is preserved using day-aware seeding logic (§8.10) — never blindly copied from a possibly stale scalar.
  • Daily usage is computed against an immutable, per-event day attribution (§8.1, §8.5) rather than being recomputed later from a raw timestamp under the device's current timezone.
  • Historical ledger data is retained only for a configured retention period, then pruned in bounded batches.
  • A battery-optimization prompt is never shown on first launch or merely because the app started. It is shown only after a corroborated gap threshold is met, is rate-limited, and respects distribution/policy eligibility. It is described to the user as addressing a detected tracking gap — never asserted to the user or in logs as a proven OEM cause.
  • Database corruption or key-access failure never results in silently creating a fresh, unrestricted database.
  • All ledger data, diagnostics, and the temporal baseline are local-only; they are excluded from Android Auto Backup (including device-transfer/cross-platform-transfer paths) and from remote crash telemetry.
  • A tracking gap never fabricates usage credit and never retroactively erases already-committed usage; if a later reconciliation determines a past total was wrong, it is corrected via an explicit compensating event (§8.12), never by editing history.

V1 scope decision (closes prior Open Question about multi-source accounting): V1 uses exactly one authoritative accounting source. No AccessibilityService is used in V1. UsageStatsManager is used only as a best-effort, clearly-labeled reconciliation source for backfilling gaps — it never independently credits usage in parallel with the authoritative source. Multi-source accounting with overlap reconciliation is explicitly out of scope for V1 and deferred to a future version if a second accounting source is ever added.

2. Requirements

Functional

  • R1 — Ledger persistence. A usage_ledger table exists in schema v11. Each row records: a stable, deterministic event_id (dedup key, §8.6), wall-clock observation time, monotonic elapsed-time-since-boot, boot count, package name, event kind, credited duration, interval start/end (elapsed-time basis), an immutable day_key, source, and source-version metadata.
  • R2 — Insert-only ledger for historical facts. The application DAO exposes insert and read/delete operations only. No update operation exists on any ACCOUNTING, DIAGNOSTIC, or MIGRATION_CARRYOVER row. A mistaken credit is fixed only via a CORRECTION row (§8.12) that references the original event — never by editing it in place. Maintenance may delete rows past retention.
  • R3 — Idempotency via deterministic identity. event_id is derived deterministically from the observation's own stable properties (source id, package, interval start/end in elapsed-time, boot count) — never a randomly generated value created fresh on every attempt. A unique index on event_id rejects duplicate inserts. Retried delivery (WorkManager retry, callback replay, service restart) reproduces the same event_id and is therefore safely ignored on retry.
  • R4 — Accounting semantics, single authoritative source. Only the one designated accounting source may write ACCOUNTING-kind events. HEARTBEAT, RULE_EVALUATION, and GAP_DETECTED kinds never contribute to the usage projection, regardless of their credited_ms value. UsageStatsManager-derived recovery data is written as RECONCILIATION kind, which contributes to the projection only for time ranges the authoritative source did not already cover (§8.9), and is deduplicated against existing ACCOUNTING rows by interval overlap, not by event_id alone.
  • R5 — Time semantics. Every accounting-relevant event stores wall-clock time, monotonic elapsed time, and elapsed-time interval start/end. Elapsed time is never subtracted across a boot-count change and treated as an exact duration. A reboot is a hard temporal boundary; the interval spanning it is reconstructed via UsageStatsManager where available, otherwise recorded as an explicit, uncredited measurement_gap.
  • R6 — Immutable day attribution. Each accounting-relevant event stores a day_key (local calendar date, computed once at interval-end time using the device's timezone offset at that moment, then frozen). An interval whose elapsed span crosses a day boundary is split into two accounting rows at ingestion time, each carrying its own day_key and its own share of credited_ms. A later timezone or manual clock change never changes a day_key already written to the ledger, and the projection is never recomputed from raw timestamps under a different timezone than the one active at event time.
  • R7 — Gap diagnostics. A gap is recorded as measurement_gap when the interval between observations from the single authoritative source exceeds the confirmed expected cadence plus a tolerance margin (§8.7). A gap may be escalated to prompt_eligible_gap once corroborating conditions are met (§8.7, replaces the previous background_execution_outage label) — this label describes prompt eligibility, not a proven cause, and must never be presented to the user, logged, or coded as an assertion that Android or an OEM killed the process.
  • R8 — Battery optimization UX. Before requesting ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS: verify the app is not already exempt (PowerManager.isIgnoringBatteryOptimizations()); verify the current build/distribution channel is permitted to use this API; require prompt_eligible_gap status; enforce a prompt cooldown. Provide a settings-guidance fallback for ineligible channels. User-facing copy describes a detected tracking interruption, not a named cause.
  • R9 — Retention. A single configuration constant defines retention duration. Pruning runs in bounded batches, is safely retryable, and is suspended (not silently applied) for a defined cool-down period after a detected large forward clock jump, to avoid deleting recent diagnostic evidence under a false "these rows are old" read (§8.8).
  • R10 — Migration. Schema version moves 10 → 11 via one explicit Migration(10, 11). No destructive fallback is registered anywhere in production code. The migration seeds the ledger from the existing v10 scalar using the day-aware algorithm in §8.10 — never a blind copy. The seeded row is written as MIGRATION_CARRYOVER kind, distinct from ACCOUNTING, and is documented as an aggregate with no reconstructable sub-timeline. The migration uses plain CREATE TABLE/CREATE INDEX (not IF NOT EXISTS) so unexpected pre-existing schema state fails the migration loudly rather than being silently masked.
  • R11 — Recovery. A database-open failure (bad key, corruption, migration failure) is classified, from the observed error signal, into the most specific category the evidence supports; when the evidence is ambiguous, it is classified as unclassified_open_failure rather than guessed into a specific category. The app never silently replaces a database containing active security rules with a blank one, in any category.
  • R12 — Enforcement under uncertainty (closes prior Open Question). When usage for the current day is partially unknown because of an unresolved measurement_gap, enforcement continues to use the last successfully committed usage_daily projection value and does not retroactively add estimated usage for the gap period. If reconciliation (via UsageStatsManager or, in a future version, another source) later determines that credited usage during the gap should be added, it is added going forward from the moment of reconciliation as a RECONCILIATION or CORRECTION event — never backdated into a way that silently changes a total the user already saw and acted on. This is a deliberate conservative default: it never causes the app to lock a user out based on estimated/unverified usage, and never causes it to silently grant extra allowance either.

Non-functional

  • No destructive migration fallback in production, ever.
  • All existing v10 data survives the migration.
  • Ledger writes are atomic (single Room transaction) and durable under the configured SQLite durability settings (§8.9, §11).
  • Duplicate or replayed accounting events never double-count usage.
  • Accounting events are structurally distinguishable from diagnostic, reconciliation, migration-carryover, and correction events via kind.
  • Time calculations explicitly account for wall-clock changes, reboot boundaries, and day/timezone boundaries.
  • Maintenance work is bounded, retryable, and never blocks the foreground enforcement path or causes an ANR.
  • No sensitive ledger content is written to remote logs, analytics, or crash telemetry.
  • The feature is local-only; nothing in this implementation introduces network transmission of ledger data. All local state related to this feature (ledger DB, wrapped key material, temporal baseline) is excluded from Android backup in every backup path the platform offers.

4. Architecture

Chosen architecture: a single-source append-only usage ledger (authoritative history) plus a transactionally-coupled current-day projection (derived, rebuildable performance cache), with an explicit compensating-event mechanism for corrections and a clearly-labeled legacy-carryover event for migration.

Components

4.1 Usage observation adapter — the one existing observation mechanism in V1. Emits raw observations only; does not decide accounting semantics.

4.2 Accounting mapper — the single place raw observations become UsageLedgerEvent domain objects. Validates package name and duration bounds, classifies event kind, attaches wall-clock time, elapsed-realtime interval start/end, boot count, computes and freezes day_key, splits any interval crossing a day boundary into two rows, and derives the deterministic event_id (§8.6).

4.3 Usage repository — the only application-level entry point for ledger writes. Owns: insert with idempotency enforcement, atomic projection update, reconstruction queries for diagnostics, correction-event insertion, and retention/prune operations. No other layer issues raw SQL against usage_ledger.

4.4 Current usage projection — a compact usage_daily(package, day_key, credited_ms, …) table. Updated in the same transaction as its triggering ledger insert. Fully rebuildable from the ledger via an explicit rebuild utility that applies ACCOUNTING, MIGRATION_CARRYOVER, RECONCILIATION, and CORRECTION kinds using the aggregation rule in §8.13, and ignores HEARTBEAT/RULE_EVALUATION/GAP_DETECTED kinds.

4.5 Diagnostic gap detector — tracks observation cadence for the single authoritative source. Its baseline state (last elapsed reading, last boot count, last wall-clock reading) is derived from the latest persisted usage_ledger row for that source — there is no separate baseline store (this closes the prior atomicity/scoping problem: the baseline can never disagree with the ledger, because it is read from the ledger). Classifies a detected gap as measurement_gap by default; escalates only per §8.7's corroboration rule, and only to a prompt-eligibility label, never a causal one.

4.6 Maintenance worker — existing WorkManager infrastructure, extended to prune ledger rows in bounded batches, suspend pruning during a clock-anomaly cool-down (§8.8), and record local pruning diagnostics. Never sits on the foreground enforcement critical path.

5. Architecture Decisions

  • AD-1 — Ledger is the source of historical truth. Fixes the core defect of the legacy scalar design; accepted storage/write cost.
  • AD-2 — Maintain a transactionally-coupled current-day projection. Avoids re-aggregating the full ledger on every enforcement check; kept consistent by updating it in the same transaction as the ledger insert; fully rebuildable.
  • AD-3 — Every accounting-relevant event has a deterministic event_id derived from stable inputs, not a randomly generated one. A random ID generated fresh on every attempt does not survive a retry of the same logical observation; a deterministic hash of source/package/interval/boot-count does.
  • AD-4 — Store elapsed-time interval start and end, not only a derived span. This is what makes day-boundary splitting (AD-6) and deterministic event identity (AD-3) possible; a bare duration is neither orderable nor splittable.
  • AD-5 — Reboot is a hard temporal boundary; cross-boot durations are never derived from wall-clock subtraction. elapsedRealtime() resets its origin on reboot and wall-clock time can move independently of it.
  • AD-6 — Day attribution is computed once at interval-end time and frozen into the row (day_key), and any interval crossing a day boundary is split at ingestion. This is what makes the projection genuinely rebuildable — recomputing "which day" from a raw timestamp under a possibly-different current timezone would silently change historical totals on replay, which is unacceptable for an audit ledger.
  • AD-7 — WAL checkpointing is left to SQLite's automatic behavior; wal_checkpoint(TRUNCATE) is never run as a routine maintenance step. Automatic checkpointing manages WAL growth in the common case; the application must still tolerate and monitor for WAL growth caused by long-running readers or large transactions rather than assuming growth is fully bounded by this alone.
  • AD-8 — No fixed PRAGMA cache_size override ships without device-class benchmark data.
  • AD-9 — auto_vacuum mode is not changed as part of the 10 → 11 migration, and storage is bounded by retention/pruning of live rows, not by expecting the .db file's high-water mark to shrink. SQLite only applies an auto_vacuum mode change via a full VACUUM. A one-time, explicitly scheduled, idle-triggered VACUUM remains a possible future maintenance operation if measured file-size growth data later justifies it (tracked in Open Questions, not built in v1).
  • AD-10 — The migration does not rotate or touch the SQLCipher key.
  • AD-11 — Migration uses an explicit Migration(10, 11) with plain (non-IF NOT EXISTS) DDL. Both automatic and manual migrations are supported by Room for this kind of change; explicit migration with strict DDL is chosen for full control over validation, the legacy-seeding step, and for failing loudly on unexpected pre-existing schema state rather than silently masking it.
  • AD-12 — The migration seeds the ledger using the day-aware algorithm in §8.10, writing a MIGRATION_CARRYOVER row, never a plain ACCOUNTING row. A blind copy of the v10 scalar risks crediting a stale (previous-day) value to the current day. The MIGRATION_CARRYOVER kind is explicitly documented as an aggregate with no reconstructable sub-timeline, so diagnostic tooling never mistakes it for a real interval.
  • AD-13 — A detected gap is stored as measurement_gap by default; escalation to prompt_eligible_gap requires the corroboration in §8.7, and neither label is ever presented — to the user, in logs, or in code comments — as a proven OEM or Android cause. The available signals (boot-count unchanged, gap duration relative to cadence, absence of recoverable UsageStats activity) establish that tracking was interrupted; they do not establish why.
  • AD-14 — Backup exclusion covers every stateful artifact this feature introduces, with no separate artifact left uncovered. Because the temporal baseline is derived from the ledger itself (AD-15) rather than stored separately, there is only one artifact to exclude: the SQLCipher database file and its wrapped key material. This is verified against both cloud-backup and device-transfer/cross-platform-transfer configuration paths.
  • AD-15 — There is no separate temporal-baseline store; the baseline is derived from the latest relevant usage_ledger row. A separate SharedPreferences/DataStore baseline created a second state machine that could desynchronize from the ledger across a crash, and left an artifact outside the single backup-exclusion boundary. Deriving it from the ledger removes both problems at once.
  • AD-16 — V1 uses exactly one authoritative accounting source; UsageStatsManager is a reconciliation-only source, never a second accounting source. This removes the need for cross-source overlap detection and reconciliation-watermarking logic in V1, which is disproportionate complexity for a single-observation-source product. Revisit only if a second real-time accounting source is added in a future version.
  • AD-17 — Accounting mistakes are corrected via an explicit CORRECTION event referencing the original event_id, never by mutating a historical row. This preserves the append-only invariant while still allowing production bugs to be fixed without permanently baking in wrong totals.
  • AD-18 — Enforcement under an unresolved measurement gap uses the last committed projection value and never estimates or backdates usage for the gap period (R12). This is the conservative default: it can never falsely lock a user out based on an estimate, and never silently grants unearned allowance either.

6. Data Flow

Normal accounting event

  1. The authoritative observation source produces a raw observation with an elapsed-time interval (start, end).
  2. Accounting mapper validates it, computes day_key from the interval's end time and the current timezone offset, and — if the interval crosses a day boundary — splits it into two rows, each with its own day_key and proportional credited_ms.
  3. Mapper derives a deterministic event_id for each resulting row from (source, package, interval start, interval end, boot_count).
  4. Repository opens one Room transaction per resulting row (or a single transaction covering both split rows together).
  5. Insert into usage_ledger.
  6. Update usage_daily projection for the row's day_key.
  7. Commit.
  8. Enforcement/UI reads the projection. Diagnostics read the ledger directly.

Duplicate delivery

  1. The same logical observation is retried; the mapper derives the same event_id as before, because it is computed from the observation's own stable properties.
  2. Unique index rejects the insert.
  3. Repository returns an idempotent-duplicate result. No projection change.

Event-ID collision with different payload

  1. An insert attempt with an already-used event_id but a materially different payload (different credited_ms, different interval) is rejected as an ID collision, not silently treated as an idempotent duplicate, and is recorded as a diagnostic anomaly for investigation — it is never silently dropped as if it were a normal retry.

Reboot

  1. New process observes a boot count different from the last persisted ledger row for the source.
  2. The interval spanning the reboot is not computed by subtracting old and new elapsedRealtime() values.
  3. UsageStatsManager is queried (wall-clock range, after confirming PACKAGE_USAGE_STATS access — §8.9) to backfill recoverable foreground activity across the boundary, written as RECONCILIATION kind.
  4. Any unresolved portion of the interval is recorded as measurement_gap tagged reboot_boundary, and per R12/AD-18, contributes nothing to the projection until/unless reconciled.

Wall-clock shift

  1. A new event's wall-clock delta is compared against its monotonic delta since the previous event from the same source (same boot only).
  2. A material conflict is recorded as a clock_anomaly diagnostic row.
  3. Usage credit always uses the monotonic-derived duration when the two disagree.
  4. No existing ledger row is ever rewritten. day_key values already frozen on prior rows are never recomputed.

Pruning

  1. Maintenance worker reads the configured retention threshold.
  2. If a large forward clock jump was recently detected (within the configured cool-down window), pruning is skipped for this run.
  3. Otherwise, deletes rows older than the threshold in bounded batches, committing each batch separately.
  4. Records batch progress locally; retries from the last committed batch on failure.
  5. A failed or delayed prune never affects current accounting correctness.

8. Detailed Implementation Steps

8.1 Ledger schema

CREATE TABLE usage_ledger (
    id INTEGER PRIMARY KEY NOT NULL,
    event_id TEXT NOT NULL,
    kind INTEGER NOT NULL,
    wall_clock_ts_ms INTEGER NOT NULL,
    elapsed_start_ms INTEGER NOT NULL,
    elapsed_end_ms INTEGER NOT NULL,
    boot_count INTEGER NOT NULL,
    package_name TEXT NOT NULL,
    day_key TEXT NOT NULL,
    credited_ms INTEGER NOT NULL,
    source TEXT NOT NULL,
    source_version TEXT NOT NULL,
    references_event_id TEXT
);

CREATE UNIQUE INDEX index_usage_ledger_event_id
    ON usage_ledger(event_id);

CREATE INDEX index_usage_ledger_package_day
    ON usage_ledger(package_name, day_key, kind, credited_ms);

CREATE INDEX index_usage_ledger_wall_clock
    ON usage_ledger(wall_clock_ts_ms);

day_key is a TEXT local-date string (e.g. 2026-09-27), computed once at write time and never recomputed from wall_clock_ts_ms later. references_event_id is populated only for CORRECTION rows, pointing at the event_id being corrected; it is NULL for every other kind. index_usage_ledger_package_day is a covering index for the daily aggregation query (package_name, day_key, filtered by kind, summing credited_ms) so that query does not require a table lookup per row.

kind values: 1 = ACCOUNTING, 2 = HEARTBEAT, 3 = RULE_EVALUATION, 4 = GAP_DETECTED, 5 = MIGRATION_CARRYOVER, 6 = RECONCILIATION, 7 = CORRECTION.

8.2 Event validation (enforced in the accounting mapper before insert)

Reject an event if: event_id is empty; credited_ms < 0; elapsed_end_ms < elapsed_start_ms; credited_ms > (elapsed_end_ms - elapsed_start_ms) for ACCOUNTING/RECONCILIATION kinds; kind is not a known value; package_name is empty or exceeds the bounded length used elsewhere in the codebase; any timestamp arithmetic would overflow a signed 64-bit value; a CORRECTION row with an empty or unresolvable references_event_id.

8.3 Current projection

Update usage_daily(package_name, day_key, credited_ms) in the same transaction as the triggering ledger insert. Implement and test a rebuild function that recomputes usage_daily purely from usage_ledger per the aggregation rule in §8.13; this function is the authoritative recovery path after corruption or a projection bug.

8.4 Temporal baseline (no separate store)

The gap detector queries the latest usage_ledger row for the authoritative source to obtain the last known elapsed_end_ms, boot_count, and wall_clock_ts_ms. There is no SharedPreferences/DataStore baseline. This guarantees the baseline can never disagree with the ledger and removes one artifact from the backup-exclusion surface.

8.5 Temporal and day-boundary rules

Within one boot: delta = currentElapsedStart - previousElapsedEnd. Reject a negative delta as an anomaly. A delta larger than the confirmed cadence plus tolerance becomes a measurement_gap. A wall-clock delta that materially disagrees with the monotonic delta becomes a clock_anomaly; credited usage always follows the monotonic delta.

Day-boundary splitting: if elapsed_start_ms and elapsed_end_ms correspond to wall-clock times on different local calendar days (computed once, at write time, using the timezone offset active at that moment), split the interval at the boundary into two rows. Each row's credited_ms is its own proportional share of the original duration. Each row's day_key is frozen at insert time and is never recomputed later.

Across a boot: never subtract elapsed-realtime values across a boot-count change. Use UsageStatsManager reconciliation where available; otherwise record an explicit, uncredited gap.

8.6 Deterministic event identity and duplicate/collision handling

event_id is derived as a stable hash (e.g. SHA-256, truncated) of: source_id + package_name + elapsed_start_ms + elapsed_end_ms + boot_count. This guarantees a retry of the same logical observation produces the same event_id.

On insert conflict:

  • If the conflicting row's other fields (credited_ms, interval bounds, kind) match the incoming event exactly → idempotent duplicate, no-op, return success.
  • If they differ → ID collision, not a duplicate. Reject the insert, record a clock_anomaly-class diagnostic distinct from a normal duplicate, and surface it for investigation. Never silently drop a differing payload as if it were a safe retry.

8.7 Gap detection, escalation, and battery-prompt gating

A gap is measurement_gap when the time since the last observation from the authoritative source exceeds the confirmed cadence (from Step 1) plus a tolerance margin (initial default: cadence × 3, subject to revision after on-device measurement — see Open Questions).

A measurement_gap escalates to prompt_eligible_gap only when: boot count is unchanged since the last observation, the gap duration exceeds the escalation threshold, and UsageStatsManager shows no recoverable activity for the interval (subject to the permission check in §8.9). This escalation is a prompt-eligibility signal, not a causal diagnosis; no code, log message, or user-facing string may describe it as a confirmed OEM or Android battery-management action.

Battery-prompt gating: not exempt already → distribution channel eligible → prompt_eligible_gap present → cooldown elapsed → show contextual education describing a detected tracking interruption (not a named cause) → offer settings-guidance fallback when the direct exemption intent is unavailable or ineligible for the channel.

8.8 Maintenance

Delete in bounded batches (fixed row-count cap per transaction, confirmed against real device testing in Step 13). Suspend pruning entirely for a configured cool-down window (default: 24 hours) after detecting a forward wall-clock jump larger than a configured threshold (default: 6 hours), so that recent diagnostic evidence is not deleted under a false "these rows are old" read caused by the jump. A failed or partial prune batch leaves the ledger consistent and retries on the next scheduled run.

8.9 Reconciliation via UsageStatsManager (V1: recovery-only, never a second accounting source)

Before querying, check AppOpsManager.unsafeCheckOpNoThrow(OPSTR_GET_USAGE_STATS) (or the current equivalent API). If not granted, record the gap as unrecoverable_no_permission and take no further action — do not throw, do not crash.

When granted: query only the wall-clock range covering an existing measurement_gap. Persist a per-source watermark (the latest wall-clock time already reconciled) so a repeated query never re-processes an already-reconciled range. Before inserting a RECONCILIATION row, check for existing ACCOUNTING or RECONCILIATION rows overlapping the same interval for the same package; if found, credit only the non-overlapping remainder, if any. Because V1 has exactly one designated accounting source and UsageStatsManager is reconciliation-only, this check only needs to guard against reconciliation being run twice — not against a second live accounting source (AD-16).

8.10 Migration seeding (day-aware, implements AD-12 — replaces the naive version)

Inside Migration(10, 11), after creating the new tables, for each package with a nonzero v10 scalar value, determine freshness before seeding:

  • If the v10 schema has an associated last-reset/last-write date or timestamp for the scalar (confirmed in Step 1): seed a MIGRATION_CARRYOVER row only if that date matches the current local day at migration time. If it does not match (the scalar belongs to a previous day and was never reset because no write occurred), seed 0 for that package and do not treat the stale value as today's usage.
  • If the v10 schema has no such date field: do not assume the scalar reflects today's usage. Conservatively seed 0, and separately log a one-time diagnostic note (locally only) recording the raw legacy value that was intentionally not carried forward, for later manual investigation if needed. This is the safe default given the original design's documented lazy-reset-at-first-write-after-midnight behavior, which makes a stale scalar indistinguishable from a fresh one without an explicit date field.

Whichever branch applies, the resulting event_id is generated deterministically as "migration_seed:" + package_name, making the migration itself safely re-runnable. The usage_daily projection row for the current day is initialized from the same value in the same transaction. A MIGRATION_CARRYOVER row is documented, in schema comments and in any diagnostic UI, as an aggregate inherited from legacy state with no reconstructable sub-timeline — it is never treated by the rebuild function or by diagnostics as a normal interval event.

8.11 Enforcement under uncertainty (implements R12/AD-18)

The enforcement path reads only the committed usage_daily projection value. It never adds an estimate for time covered by an unresolved measurement_gap. If UsageStatsManager reconciliation later resolves part of a gap, the resulting RECONCILIATION credit is added to the projection at the moment reconciliation completes, going forward — it is not backdated in a way that changes a total already shown to or acted on by the user for a prior moment in time.

8.12 Corrections

A CORRECTION row references an existing event_id via references_event_id and carries a signed credited_ms value (positive or negative) representing the adjustment. It contributes to the projection like any other accounting-relevant kind, applied in insertion order. The original referenced row is never edited or deleted by a correction.

8.13 Aggregation rule (used by both the live projection updater and the rebuild utility)

For a given (package_name, day_key), the total is the sum of credited_ms across all rows of kind ACCOUNTING, MIGRATION_CARRYOVER, RECONCILIATION, and CORRECTION matching that scope. Rows of kind HEARTBEAT, RULE_EVALUATION, and GAP_DETECTED are always excluded. This single rule is used identically by the transactional projection updater and by the standalone rebuild function, so the two are guaranteed to agree by construction.

8.14 Database configuration

Use Room/driver-supported configuration APIs; do not set raw per-connection PRAGMAs unless confirmed to apply consistently to every connection Room/SQLCipher opens. WAL mode is required going forward; confirm in Step 1 whether it is already enabled and, if not, enable it explicitly rather than leaving it implicit. synchronous = NORMAL is used under WAL, with the accepted durability trade-off documented explicitly: recently committed transactions can be lost on a kernel panic or sudden power loss, but the database itself remains structurally consistent; this is an accepted trade-off for this feature's data (usage diagnostics), not for anything else in the app. auto_vacuum is not changed by this feature (AD-9). cache_size is not overridden without benchmark evidence (AD-8).

9. Error Handling

Migration failure: propagate the failure; leave the original v10 database files untouched (the migration runs inside Room's own migration transaction, which rolls back on failure); record a local diagnostic code; do not fall back to destructive recreation.

Duplicate event: idempotent no-op, per §8.6.

ID collision (differing payload, same derived ID): reject the insert, record a distinct diagnostic anomaly, never silently drop.

Database locked/busy: rely on the configured busy-timeout; keep every application-level write transaction short.

Disk full: treat SQLiteFullException (or equivalent) as a real persistence failure. Do not silently discard a rejected accounting event. Attempt bounded maintenance if safe. Surface a degraded-tracking indicator to the user rather than pretending the write succeeded; enforcement continues per §8.11 using the last committed projection.

SQLCipher key failure: classify from the observed error signal into the most specific category the evidence supports (missing key material, invalid key, format/integration mismatch, likely corruption); classify as unclassified_open_failure when the evidence is ambiguous rather than guessing a specific category. Never auto-generate a fresh database when the existing one contains active security rules.

Database corruption: never auto-quarantine-and-replace with a blank database if doing so removes active protections, in any failure category. Recovery is fail-closed by default pending resolution of Open Question 5 (below).

Unexpected temporal state (negative elapsed delta, unavailable boot count, unexpected boot-count change, drastic wall-clock jump, timezone change mid-interval, overlapping intervals): record the specific anomaly type; never invent a duration to fill the gap; never double-credit.

10. Security Requirements

  • SQLCipher encrypts the database file at rest. This protects against offline file extraction only — it does not protect against a compromised, rooted, or instrumented live process that has already obtained a valid database key. Document this scope explicitly in code comments and any security review artifact.
  • Reuse the existing, already-stable SQLCipher key-provisioning path; this feature does not introduce a new key-wrapping layer.
  • PRAGMA integrity_check is used as an on-demand diagnostic tool, not a mandatory every-launch gate. SQLCipher's HMAC provides tamper detection on encrypted pages; it does not authenticate application-level event sources and provides no anti-rollback protection.
  • Never log: full ledger rows, per-package usage history, SQLCipher passphrases, wrapped key material, decrypted key bytes, or raw database contents, in any logging or crash-reporting sink.
  • Verify the exact SQLCipher build's temporary-storage (temp_store) configuration during Step 1, and confirm large queries/sorts cannot spill plaintext data to unencrypted temporary files.
  • Exclude the SQLCipher database file and any wrapped key material from Android Auto Backup, and separately verify device-transfer and cross-platform-transfer configuration paths exclude the same artifacts. Because the temporal baseline is derived from the ledger (AD-15), there is no second artifact to separately exclude.
  • Use parameterized/bound queries for all dynamic SQL. Never interpolate package name, source, or any user- or device-derived string into a SQL statement.
  • Pin the exact SQLCipher and Room artifact versions used; verify the resulting native library against current platform compatibility requirements (§13).

11. Performance Requirements

  • Measure, on at least one representative low-end device: single-event insert latency (including day-boundary-split cases), batched-insert latency, transaction latency including the projection update, and WAL growth under realistic event rates.
  • Measure read latency for: current-day projection read, single-package ledger reconstruction, multi-package history reconstruction, and prune-candidate selection — using the covering index in §8.1.
  • Capacity model to validate before finalizing retention/cadence values: retained_rows ≈ event_rate × tracked_package_count × retention_duration, using the actual confirmed cadence from Step 1 (see Open Questions if not yet confirmed).
  • Measure prune-transaction duration, WAL growth during pruning, and CPU cost of SQLCipher encryption overhead under the batch sizes chosen in §8.8, on representative low-end hardware.
  • Measure SQLCipher's memory footprint (page cache, crypto context) on a low-RAM device class alongside the query-latency measurements, since this can contribute to OOM risk independent of cache_size tuning.

12. Testing Requirements

Migration: v10 database opens; all v10 data survives; v11 schema matches the exported schema JSON; usage_ledger and its indexes exist; unique event_id constraint is enforced; the day-aware seeding algorithm (§8.10) is exercised for: scalar with a matching current-day date field, scalar with a stale prior-day date field, scalar with no date field at all, and zero-usage case; a mid-migration failure rolls back cleanly leaving the original v10 state (replaces the earlier "idempotent re-run" framing, which does not apply to a normal Room version transition); encrypted SQLCipher driver opens the migrated database; no destructive fallback path is exercised.

Ledger behavior: insert one event; insert an exact duplicate (event_id matches, payload matches — idempotent no-op); insert an ID collision (event_id matches, payload differs — rejected and flagged); insert across multiple packages; zero-duration event; negative-duration event (rejected); unknown kind value (rejected); interval crossing a day boundary (verify correct split and correct day_key on each half); a CORRECTION row referencing a real prior event (verify projection reflects the signed adjustment); a CORRECTION row with an invalid reference (rejected).

Concurrency: multiple threads submitting distinct events; multiple threads submitting the same logical (and therefore same-ID) observation; concurrent reader + writer; concurrent maintenance job + accounting write.

Time: normal monotonic progression; wall-clock moved backward; wall-clock moved forward; timezone change mid-day (verify already-written day_key values are untouched and the rebuild function reproduces the same totals regardless of current timezone); reboot; elapsed-time reset after reboot; very large observation gap; out-of-order event arrival; large forward clock jump (verify pruning suspension per §8.8).

Reconciliation: UsageStatsManager permission denied (verify graceful unrecoverable_no_permission classification, no crash); permission granted with recoverable data; repeated reconciliation of an already-reconciled range (verify watermark prevents double-credit); reconciliation overlapping an existing ACCOUNTING row (verify only the non-overlapping remainder is credited).

Process lifecycle: process killed between observation and insert; process killed mid-transaction; app resumed after a long background period; database temporarily unavailable while tracking continues.

Maintenance: no rows to prune; large row count to prune; prune interrupted mid-batch and retried; new events arriving during a prune run; database nearly full; database full; pruning correctly suspended during the clock-anomaly cool-down window.

Recovery: invalid SQLCipher key; missing wrapped key; corrupted page; corrupted schema metadata; migration failure path; app-binary rollback attempted against a v11 database (verify it is prevented per §13, not handled via destructive downgrade).

Battery prompt: no prompt on first launch; no prompt while already exempt; no prompt for a gap within the confirmed normal cadence plus tolerance; prompt fires only once prompt_eligible_gap is set; cooldown enforced after a decline; settings-guidance fallback exercised when the direct exemption intent is unavailable/ineligible; verify no user-facing string or log line asserts a specific cause.

Invariant/property tests (must hold in every run):

  1. Retrying the same logical observation never increases total credited usage.
  2. The usage_daily projection total always equals the sum computed by the standalone rebuild function using the §8.13 rule, for every scope.
  3. Removing diagnostic-only rows (HEARTBEAT, RULE_EVALUATION, GAP_DETECTED) from the ledger never changes any projection total.
  4. No monotonic interval is ever negative across a reboot boundary.
  5. No historical usage_ledger row of kind ACCOUNTING, MIGRATION_CARRYOVER, RECONCILIATION, or CORRECTION is ever mutated by routine accounting or maintenance code.
  6. Pruning never removes a row newer than the configured retention cutoff, and never runs at all during an active clock-anomaly cool-down.
  7. The migration never deletes any pre-existing v10 rule/user data.
  8. Every user with a v10 scalar value that the day-aware algorithm determines to be current-day has a correctly seeded MIGRATION_CARRYOVER row and correctly initialized usage_daily value; every user whose scalar is determined stale or undated is seeded at 0, not the stale value.
  9. An interval crossing a day boundary always produces exactly two rows whose combined credited_ms equals the original interval's duration, with no double-counted or lost milliseconds.
  10. A day_key value, once written, is never recomputed even if the rebuild function is later run under a different device timezone.

13. Deployment Requirements

  • Test the v10 → v11 upgrade against a real, production-shaped v10 database, including devices with nonzero accumulated daily usage at migration time under all three seeding scenarios in §8.10.
  • Test cold start immediately after migration.
  • Test on low-storage devices.
  • Test on at least one physical device per major OEM battery-management variant available for testing.
  • Because database downgrade is unsupported, the release process must prevent a v10 binary from ever being distributed against a device that already holds a v11 database. Do not implement a destructive downgrade path as a workaround.
  • Verify the shipped native SQLCipher library is compatible with current Android/Google Play platform requirements for apps containing native code, including 16 KB memory page-size device support; test on a 16 KB-page emulator or device before release.
  • Roll out in stages. The first monitoring cohort must be large enough to reach multiple Android vendors and hardware tiers before expanding further; expand based on the monitoring signals below being clean, not on elapsed time alone.
  • Monitor during rollout: migration failures (including which seeding branch of §8.10 was taken, in aggregate), database-open failures, SQLCipher key errors, SQLITE_BUSY/SQLITE_FULL/constraint-violation errors, ANRs, usage-discrepancy reports, ID-collision count, ledger row-count growth, maintenance job failures, and measurement-gap frequency.

14. Monitoring Requirements

All monitoring is local-only; this feature does not add remote telemetry.

Local counters/metrics to maintain: ledger insert failures, duplicate-event count, ID-collision count, measurement-gap count, prompt-eligible-gap count, largest recorded gap, reboot-boundary count, clock-anomaly count, forward-clock-jump count (and resulting pruning suspensions), prune success/failure count, database-busy count, database-full count, key-open-failure count (by classification), projection-rebuild invocation count, reconciliation-credit count, correction-event count.

Do not retain unbounded diagnostic history outside the ledger itself — these are bounded counters, not a second log.

Remote crash telemetry (if the app already uses a crash-reporting SDK): verify, before release, that its configuration scrubs SQL statement text, database file paths, per-package usage arrays, ledger row payloads, and any cryptographic key material from captured reports.

17. Acceptance Criteria

  1. A real, production-shaped v10 SQLCipher database upgrades to v11 without any loss of existing rule or user data.
  2. The database opens with the same valid key immediately after upgrade.
  3. Every accounting-relevant event has a deterministic event_id; a retry of the same logical observation reproduces the same ID and never double-credits.
  4. A differing payload under a colliding ID is rejected and flagged, never silently dropped as a duplicate.
  5. No diagnostic-kind event ever contributes to the usage projection.
  6. The usage_daily projection and the standalone rebuild function agree, for every scope, in every test run.
  7. No reboot boundary ever produces a negative or fabricated monotonic interval.
  8. A manual wall-clock change never creates usage credit derived from a raw wall-clock subtraction.
  9. A day_key value, once written, is never changed by a later timezone change or by a rebuild run under a different timezone.
  10. An interval crossing midnight is split into two correctly-attributed rows with no lost or duplicated duration.
  11. A measurement gap is never automatically re-labeled a confirmed OEM/Android cause, in code, logs, or user-facing copy.
  12. Battery-optimization prompts are gated, corroborated, rate-limited, and channel-eligibility-checked before appearing.
  13. No destructive migration fallback is registered anywhere in the codebase.
  14. The migration's day-aware seeding algorithm correctly handles all three cases in §8.10 (dated-and-current, dated-and-stale, undated), verified by invariant test #8.
  15. Enforcement never estimates or backdates usage for an unresolved measurement gap.
  16. A reconciliation credit is never applied twice for the same interval.
  17. A production accounting mistake can be corrected via a CORRECTION event without mutating any historical row.
  18. No routine maintenance path requires a full-database VACUUM or calls wal_checkpoint(TRUNCATE).
  19. No fixed cache_size override ships without accompanying benchmark data.
  20. A classified key-failure or corruption event never silently deletes or replaces a database holding active security rules.
  21. No sensitive ledger content appears in logs or crash-telemetry payloads.
  22. The SQLCipher database file and wrapped key material are confirmed excluded from Android Auto Backup and from device-transfer/cross-platform-transfer paths; there is no second stateful artifact left uncovered, since the temporal baseline is derived from the ledger.
  23. The shipped native library is verified compatible with 16 KB page-size devices.
  24. All tests listed in §12 pass against the real SQLCipher/Room stack, including all ten invariant tests.
  25. No unrelated component, table, or workflow outside the scope of §3 is modified.
